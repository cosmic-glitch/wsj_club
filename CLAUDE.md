# WSJ Reading Club

A daily reading-handout website for a small club of four kids in US grades 8–10. Each day = one Wall Street Journal article turned into a study handout with two sections — **Words to know** and **Concepts behind the story** — plus a **self-quiz** on its own page. Goal: build general knowledge, vocabulary, and conceptual understanding.

Live: https://wsjclub.vercel.app · Repo: https://github.com/cosmic-glitch/wsj_club

## Architecture

Next.js app (App Router, Next 16, React 19, Tailwind v4). The daily content is **data, not code**: one JSON file per day in `content/`. The content pages (index, handout, quiz) are **statically generated** — adding a day = adding one JSON file. The **voice-quiz feature** (see below) adds a handful of **dynamic server routes** (login, per-turn tutor/TTS/transcribe, audio-upload token, report card) and an admin page, so the app is no longer purely static, but every content page still prerenders.

### Tracks (senior + junior)

There are **two reading tracks**, sharing the same site, logins, classrooms, and Scores page: **senior** (the original club, US grades 8–10, at `/`) and **junior** (US grades 5–7, at `/junior`, occasional). `type Track = "senior" | "junior"` (`lib/content.ts`) is a first-class dimension because **`date` is no longer a unique key** — a junior article almost always lands on a date that already has a senior one. **Senior keeps every path exactly as it was; only junior takes a `junior/` path segment**, everywhere: content (`content/junior/<date>.json`), PDFs (`public/pdfs/junior/`), audio (`public/audio/junior/`), article text (`article-text/junior/<date>.txt`), every Blob session/slot key (`quiz-sessions/junior/<date>/…` — via `sessionPrefix(track, date)` in `lib/session-io.ts`), and the vote blobs (`votes/junior/<date>/…` — see the Daily vote section), plus the routes (`/junior`, `/junior/reading/<date>`, `/junior/reading/<date>/quiz`) and the resume deep-link (`/junior?resume=<date>`). This means **zero backfill and zero change to existing senior URLs/data** — junior is purely additive.

The pieces are threaded through by `track`: the **shared page components** (`components/LandingIndex.tsx`, `Handout.tsx`, `SelfQuiz.tsx`) take a `track` prop and each track's route is a thin wrapper; the **quiz API routes** parse `track` from the request body/query (defaulting to `"senior"` at the API boundary) and pass it to `getReading(date, track)` / `getArticleText(date, track)` / the session-key helpers; the **client** (`components/VoiceQuiz.tsx`) takes a `track` prop and sends it on every API call and in each upload's `clientPayload`; the **tutor + grader** swap only the **audience band** (grades 5–7 vs 8–10 — `AUDIENCE` in `lib/quiz-prompt.ts`; nothing else about grading changes — same calibration anchors, same +1 leniency); saved sessions are **stamped `track: "junior"`** (senior omits it — absent means senior), which drives a **`junior` badge** on Scores and keeps `groupByArticle` from merging a junior + senior attempt on the same date. **Identity always comes from the cookie**, never the body — `track` is only a label (a forged track reaches only the caller's own junior path). The **`sessionPrefix` + every slot helper takes a REQUIRED `track`** (no `"senior"` default) so the compiler enumerates every call site — a defaulted helper would silently compute the senior path at a junior call site and, since the slot flush is best-effort, fail invisibly (a lost junior recording / an orphaned junior slot). See `PLAN-junior.md`.

## Content schema (`lib/content.ts`)

A `Reading` = `{ date, title, articleUrl?, pdfUrl?, articles?, voiceQuiz?, source?, vocab[], concepts[], quiz[] }`.

- **articleUrl** — the WSJ web article (the **Web** link). **pdfUrl** (optional) — a served PDF of the article, e.g. `/pdfs/2026-06-09.pdf` (the **PDF** link); omit it and only the Web link shows.
- **voiceQuiz** (optional `boolean`) — when `true`, the home-page row for that day shows the AI-oral-quiz launcher in its action bar **to everyone** (signed in or not); clicking it while logged out pops a login prompt instead of starting. The skill sets `voiceQuiz: true` on every new day. It is now set on **every day** — the earlier pre-feature days (2026-06-09 → 2026-06-17) were backfilled, so all entries have the voice quiz for logged-in users.
- **clubPick** (optional `boolean`) — when `true`, the day's article was chosen by the **daily vote** (see that section): the index row shows a small bordered **CLUB PICK** chip next to the title, a permanent record of the club's picks. Set by the wsj-reading / wsj-reading-junior skill on a vote day (a poll exists for the date on that track); omitted on normal days.
- **articles** (optional) — for **multi-article days**: bundle two or more short articles into one combined handout. It's an array of `Source` = `{ title, articleUrl, pdfUrl? }` (each article's own headline + links). When `articles` is set, the top-level `articleUrl`/`pdfUrl` are unused, the vocab/concepts/quiz are **combined** across all the articles, and each article gets its own PDF named `/pdfs/YYYY-MM-DD-1.pdf`, `-2.pdf`, … (see `content/2026-06-14.json` for the first one). Most days are single-article and just use `articleUrl`.

- **Announcements** (site-wide, not part of `Reading`) — a single **announcement banner at the top of the home page** replaces the old per-day `note` field (removed everywhere — schema, page, content files). Content lives in **`content/announcement.json`** = `{ messages: string[] }`, loaded by `getAnnouncements()` in `lib/content.ts` (the readings loader only matches date-named `YYYY-MM-DD.json` files, so this file is never parsed as a day). The banner is an amber card labeled **"Announcement"** (singular) rendered above the row-list, the messages as a bulleted list (one bullet per message); an empty `messages` omits it entirely. It's edited in place — used to announce the latest features (e.g. voice-quiz pause & resume) or give reading guidance for today's article (the job the old `note` did, e.g. "read the Concepts section of the handout before the article").

- **vocab** — **usually 3** `VocabWord`s (the `wsj-reading` skill's default recommendation; the author can and does override the count every few days — the pages and voice quiz handle any number via `reading.vocab.length`, so some days run 4+), each presented *article-first*:
  `articleQuote` (short real quote from the article) → `inContext` (what it means there) → `meaning` (broader definition) → `examples` (exactly **2** more example sentences). Each also carries `pronunciation` — a plain-English US respelling (hyphen syllables, primary stress in CAPS, e.g. `"yoo-BIK-wih-tus"`; NOT IPA) shown on the card in place of the part of speech — and `partOfSpeech`, kept in the JSON for the voice-quiz tutor but no longer shown on the handout.
- **concepts** — **up to 3** `Concept`s (take as many strong, transferable ideas as the article genuinely supports, capped at three; fewer is fine and a vocab-only day runs `[]` — see below — never pad to hit a number; the count is user-overridable). **Unlike vocab, a concept is NOT split into "what it means here" vs "in general"** — it's `articleQuote` (the anchor) → a **single, unified `meaning`**. That `meaning` is written **Feynman-style**: start from intuition with a vivid hook/analogy that makes the idea click, explain how it actually **works** in plain language, and **ground it with at least one concrete example** (school/sports/social-media/money situations a teen pictures instantly). It may hold **multiple paragraphs** (blank-line split — `ConceptCard` renders each `\n\n` chunk as its own `<p>`, now with **no** "In general:"/"What it means here:" labels — just the explanation under the quote). `inContext` is a **legacy optional field** — older entries still carry it (it's kept in their JSON) but it is **no longer rendered**; new concepts omit it. A concept may also carry an **optional `link` (`{ url, label }`)** — an illustrative external link rendered as an amber button under the meaning (e.g. a live prediction-market page); omit it and nothing shows. Both the single-explanation shape and the first `link` landed on `content/2026-07-09.json` (the Polymarket day — Feynman rewrites + the live 2028-election market link). **May be empty (`[]`) for a vocabulary-only day** — when an article is vocab-rich but thin on transferable concepts, it's better to drop the section than to ship weak, topic-bound concepts. An empty `concepts` is handled everywhere: the handout **omits the "Concepts behind the story" section** (and drops the lone step-number on the words section), and the voice quiz **skips its concepts stage** — `buildInstructions`/`buildReportPrompt` in `lib/quiz-prompt.ts` branch on `concepts.length` so the tutor never quizzes (and the grader never penalizes) concepts that don't exist. The first such day is `content/2026-06-24.json`. The tutor's **concepts stage scales to the count** too: a **single-concept day** (e.g. `content/2026-07-18.json`, 5 vocab / 1 concept) gets a **singular stage** ("there is exactly ONE concept … then you are DONE with concepts — do not re-ask it or invent extra concepts"), while **2+ concepts** keep the "ask about at least TWO **different** concepts, never re-ask/re-word one" quota. This fixed a live bug: the old stage hardcoded "ask about at least TWO," which is impossible on a 1-concept day, so the tutor re-asked the sole concept verbatim (and promoted a vocab word to a pseudo-concept) to fill the quota — Samaira's 07-18 "Soft power" attempt caught it. Most days run up to 3 concepts (some fewer; a vocab-only day runs 0).
- **quiz** — exactly **5** `QuizQuestion`s, each `{ question, options (4), answerIndex (0-based), explanation }`.

Pages stay minimal. The **index** is a **compact row-list, one row per day** (a `<ul>` inside a single thick-bordered card, newest first; since the brutalist redesign each row's actions are **boxed uppercase buttons** — WEB / PDF / HANDOUT / AI QUIZ — rather than the middot-separated text links described in the history below). It replaced the earlier tall "one box per day" cards: those were ~8 lines each and scrolled badly as the list grows. The design intent was a **table**, but a literal `<table>` was rejected — a table shares column widths across all rows, so one long headline squeezes the action columns and forces **horizontal scroll on a phone** (the same problem that had earlier killed a six-column table). The row-list gets table-like compactness *without* that: each row's action bar simply **wraps** to a second line on narrow screens instead of scrolling. Each row is the **date** (a muted serif label, `dateBig`) + the **article title** as plain text (**not** a link) on one prominent line, then a small **action bar** of text links separated by middots (`·`): **Web link** — the mobile-aware `ArticleLink` — then a separate **PDF** link (its own middot-separated item, **not** a parenthetical "(PDF)") when `pdfUrl` is set; multi-article days (when `articles` is set) show "Web link 1 · PDF 1 · Web link 2 · PDF 2 · …", one numbered pair per source; then **Handout**; then **Voice quiz** (shown to everyone — see below). The separating middots carry generous horizontal margins (`mx-2.5`) so each action reads as a distinct, separately tappable target with clear breathing room on a phone, where the bar wraps. There is **no self-quiz and no 1-1-quiz (Calendly) link on the index** anymore — the self-quiz moved to a CTA at the **bottom of each handout** (`/reading/<date>/quiz`, every day has one), and the Calendly 1-1-quiz link was dropped from the index entirely (it is no longer linked anywhere). The **Voice quiz** is a small client component, `components/VoiceQuizStep.tsx`: it's one more middot-separated action-bar item that **brings its own leading `·`** and is shown to **everyone**, signed in or not (it shows for any day with `voiceQuiz: true`). The login check happens **on click**, inside `VoiceQuiz`'s `launch()`: a signed-out visitor who clicks it gets a "You need to log in" popup instead of starting a session, so the public can see the feature but can't run up OpenAI charges. (Login state is still fetched **once** for the whole page by `AuthProvider` — a client context wrapped around the app in `app/layout.tsx`, which the header/topline `HomeAuthBar` and each `VoiceQuiz`'s click-handler read from — not per row; before that, every day's `VoiceQuizStep`+`VoiceQuiz` and the old header `AuthControl` each fetched `/api/me` independently, so on a logged-in home page a dozen-plus identical requests fired.) (The launcher button in `VoiceQuiz.tsx` is styled as a text link so it sits inline in the bar.) The handout top is **just the article title** (no date), then the two sections, then the **"Take the self-quiz →" CTA**. **Navigation is deliberately sparse:** the WSJ article link lives only on the index (in each row's action bar), and the way back to the index from any inner page is the header's "RC" monogram (`components/SiteHeader.tsx`; the old separate "← All readings" link — `components/AllReadingsLink.tsx` — was removed to unclutter the header on phones) — content pages (handout, quiz) carry no inline back-link of their own. No summary/blurb, no reading-time estimate. Both vocab and concept cards open with the quote labeled **"Quote from the article"**. A **vocab** card's header shows the word, then its **plain-English pronunciation respelling** (e.g. "rih-PUG-nunt") where the part of speech used to be, then the ▶ audio button; it then shows the two-part **"What it means here"** (in the article) → **"In general"** (broader meaning), plus its examples list. **Concepts differ**: after the quote they show a **single, unlabeled Feynman-style explanation** (the `meaning`) — no "What it means here"/"In general" split (that split was dropped for concepts; the legacy `inContext` is no longer rendered).

## Voice quiz (beta)

A "Voice quiz" feature that automates the teacher's 1-1 oral quiz: a student clicks the **Voice quiz** link in that day's row on the home page and an AI tutor quizzes them aloud about that day's article in a modal, then a report card is generated and saved. It runs **turn by turn, fully under the student's control** — the tutor's question appears on screen and is spoken aloud (OpenAI **TTS**; the fixed opening turn is shown but **not** spoken, only later follow-ups are), the student presses **Start speaking** to record their answer and **Stop** when done (a state toggle, not press-and-hold), the answer is transcribed (OpenAI **speech-to-text**) and shown on screen, and a **chat model** decides the next question — repeating until the tutor signals the quiz is complete, at which point the **End quiz** button appears for the student to press (before that the live screen shows Start speaking + Save for later + Cancel, so End can never truncate an answer in flight — see *Strict End gating*). There is **no realtime/WebRTC speech-to-speech session and no model-driven turn detection** (an earlier build used OpenAI's Realtime API with `semantic_vad`; letting the model guess when the student had finished was unreliable, so turn-taking moved to explicit buttons). **At the end the student is shown their full report card** — the same score + summary + strengths/gaps the teacher sees on `/admin` — plus an invitation to retake the quiz if they're not happy with it. The student now also **sees their own transcribed answers** as they go (and the tutor's questions); the full transcript and the **audio recording stay private (teacher-only)** and are captured to Blob for review on `/admin` (the live screen tells the student their answers are recorded). The **voice-quiz action is shown to everyone** — signed in or not (`components/VoiceQuizStep.tsx`) — for any day with `voiceQuiz: true`, and it is the **last item in the day's action bar** ("Web link · PDF · Handout · Voice quiz"). The login gate is **on click**: clicking the voice quiz while logged out pops up a "You need to log in" message rather than starting, so the public can see the feature but can't run up OpenAI charges without logging in.

- **Auth gates it.** The whole site is public to browse, but starting a quiz requires login (a header **Log in** control). This is what stops the public from running up OpenAI charges. **Users live in a Blob-backed repository** (`lib/users.ts`) — one record per login at `users/<username>.json` = `{ username, displayName, passwordHash, role: "teacher"|"student", teacherId?, active, createdBy, createdAt }`. This is the **source of truth**; `lib/auth.ts` keeps the cookie/HMAC machinery and derives identity/role by looking the user up there. Passwords are stored only as **bcrypt hashes** (bcryptjs, 10 salt rounds — same scheme as the foliotracker project), never plaintext, never in source. Login sets a signed httpOnly cookie (HMAC with `AUTH_SECRET`) carrying just the username; role/classroom are looked up fresh (`currentUser` also rejects a **deactivated** user even with a valid cookie). See **Classrooms** below for the teacher↔student model. **Transitional fallback:** a username not yet in `users/` falls back to the legacy `AUTH_USERS` (base64 JSON `{ username: bcryptHash }`) + `ADMIN_USERS` env vars, so a mid-rollout gap can't lock anyone out — removable once the seed is confirmed in prod. (Base64 because bcrypt hashes contain `$`, which Next's `.env` loader would expand.) `scripts/hash-password.mjs` still hashes a plaintext into an `AUTH_USERS` value; new users are normally created through `lib/users.ts` (Phase 2 UI) instead.

- **The flow** (`lib/quiz-prompt.ts`, `buildInstructions`): a short **opening** turn — just "Hi <name>" (it does **not** name the article, since the title is already on screen) plus the first task ("explain the key ideas, as much as you remember, bring in as many layers as you can; take your time, pauses/ums are fine"). The opening line is a fixed script, **identical every quiz and already on screen, so it is NOT spoken** — the student just reads it and presses Start speaking; **only the tutor's later, dynamic follow-ups are spoken** (kept short on purpose so their TTS is quick). The **recording mechanics are also NOT spoken** — they're shown on screen as a small helper line under the Start speaking button (`RecordingHelp` in `VoiceQuiz.tsx`: "press **Start speaking**, wait until it shows **Recording**, then talk; press **Stop** when done — or **Pause** if you get interrupted; same for every question"), visible on every turn → the student's from-memory **key ideas** retelling, which the tutor **listens to without interrupting** and then **judges generously** (no nitpicking, no expecting every detail; it just checks they covered a good number of the article's real ideas and went **beyond the obvious title**). The bar is a good reading by a typical 8th–10th grader (not a perfect summary): if the retelling clears it, the tutor **moves on with NO follow-up at all**; only if it was clearly wrong or significantly lacking does the tutor ask **exactly ONE broad, thematic follow-up** (about the big picture / main point — never a narrow hunt for a specific name, number, or event), and then **moves on regardless of how that answer went** — a remaining gap just lowers the score, it never earns a second question (no repeated back-and-forth). **At the end of the key-ideas round, if an area was weak the tutor gives a brief "educational update" (a one-or-two-sentence mini-lesson, a statement not a question) before moving on** → **vocabulary** (meaning or use-in-a-sentence for each of the day's vocabulary words — usually 3) → a few **concepts** from the handout (**each concept is its own turn — asked AND answered — before the wrap-up**) → short encouraging wrap-up that ends by telling the student, word for word, "The quiz is done. You can press the End Quiz button." (this wrap-up is a **question-free turn of its own** — the tutor must **never bundle a question into the same turn as the wrap-up / `done` signal**; a 2026-07 prompt fix after a quiz skipped straight from vocab to a lone concept-question-plus-`done` turn, ending the student *before* she could answer and then grading her down for the unanswered concept. The wrap-up turn carries the `done` flag, which is what makes the **End quiz** button appear; the student then clicks it — there is no auto-end). The day's vocab/concept *meanings* are injected as the tutor's answer key. A high-level **style guide** (Socratic, one question at a time, hint-don't-reveal, stay on-article, **patient listening — never interrupt**, and **"coach the gaps"** on the **words and concepts** — whenever the student is wrong or half-right there, **ask a guiding follow-up question first** and only *tell* them the correct version if they still don't get it after that; the **key-ideas round is the exception** — at most ONE broad follow-up, then move on) lives in `STYLE_GUIDE` in that file — tune it there.
- **Full article text (the tutor's reference).** When available, the tutor is given the **whole article as plain text** (plus the full handout), so on the key-ideas step it *listens to the student's entire from-memory retelling without interrupting*, then judges it against the real story — accepting imperfect recall but expecting a few non-obvious points beyond the headline, and only probing afterward. The text is **not committed** (CLAUDE.md hard rule: never republish article text); it lives in **Vercel Blob** at `article-text/<date>.txt` (`lib/article-text.ts` reads it; `getArticleText` returns null → handout-only fallback for days without it). Upload it with `pdftotext public/pdfs/<date>.pdf article-text/<date>.txt` then `node --env-file=.env.local scripts/upload-article-text.mjs <date>` (the `/article-text/` dir is a gitignored drop-zone). This upload is now **part of the wsj-reading skill** (step 3), so every new day gets it. So **every day has full article text** in Blob.
- **Turn-taking is button-driven, never inferred.** The student decides when each of their turns starts and ends by pressing **Start speaking** / **Stop**, so the tutor can never cut in (the whole point of moving off the realtime model). This makes the patient-listening rule structural rather than a model setting: the long key-ideas retelling simply runs as long as the student holds the floor. The trade-off is latency — after **Stop**, the turn does **transcribe → next-question → TTS** sequentially (~3–6s of "Transcribing… / Thinking…"), which is fine for a quiz and far cheaper than per-minute realtime. The live screen shows explicit status for each of those steps. A recording can also be **paused mid-answer** (a **Pause** button next to Stop — for real-world interruptions; `pauseSpeaking`/`resumeSpeaking` in `VoiceQuiz.tsx`): NOT a new phase, just a `recPaused` sub-state of `recording` — Stop and Cancel keep working from it, and Save for later stays unavailable (the in-flight answer isn't transcribed yet; to leave, Stop first). Nothing is captured while paused — the clip and the on-screen timer both exclude the gap (desktop pauses the per-turn `MediaRecorder`; iOS stops appending PCM samples with the mic/graph left in place), the meter goes grey + flat, and a helper line says nothing is being recorded. **Resume on iOS recovers a capture session that died during the pause** (screen lock / app switch can suspend the context or mute the track): it resumes the context and, if the track is no longer live, re-acquires a fresh mic into the same ScriptProcessor — the samples captured before the pause are kept either way; on failure an amber notice says to try Resume again or Stop.
- **How it connects.** `components/VoiceQuiz.tsx` (client) renders the **Voice quiz** launcher (a link-styled button) as the home-page row's voice-quiz action-bar item (wrapped by `components/VoiceQuizStep.tsx`, which just supplies the leading middot — the launcher shows for everyone). It reads login state from the shared `AuthProvider` context (one `/api/me` fetch for the whole page; login/logout reload the page, so it stays fresh) and gates on click: logged out → a "You need to log in" modal; logged in → it first **probes for a saved in-progress attempt** (`GET /api/quiz-progress?date=` — a slot pops the **Continue / Start over** chooser, see *Pause & resume* below; the launcher label always stays "Voice quiz"), then opens the quiz, grabs the mic (the click is the user gesture that also lets audio play), and uses the **login username** as the student name. The quiz then runs as a **turn loop** managed by a `phase` state machine (`starting → tutorTurn → recording → transcribing → thinking → …`, plus `probing`/`chooser`/`paused`/`leaving`/`wrapup`/`error`): (1) **`/api/quiz-turn`** is POSTed the running transcript and returns the tutor's next line **plus a `done` flag** — its system prompt is `buildInstructions` with the day's full article text pulled from Blob, so the chat model judges answers against the real story. The tutor replies as structured **`{text, done}` JSON** (`response_format: json_object`); the route parses the **first balanced `{…}` object** out of the completion (`parseTutorReply` / `firstJsonObject` in `app/api/quiz-turn/route.ts`, string/escape-aware), so a model that occasionally **emits two JSON objects back-to-back or wraps the object in stray prose** still yields a clean spoken line instead of **leaking raw JSON aloud** — a real recurring glitch (seen across ~8 sessions) that a plain `JSON.parse` of the whole completion turned into the spoken text. `done` is `true` **only on the final wrap-up turn** (with an exact-wrap-up-phrase fallback if the model omits the flag, and a one-shot retry on an empty completion before a 502), and it is what unlocks the End quiz button — see *Strict End gating* below; (2) the line is shown in an on-screen conversation log and spoken via **`/api/quiz-tts`** (mp3 played through a hidden `<audio>`; best-effort — if TTS fails the student just reads it) — **except the opening turn, which is shown but not spoken** (see the fast path below); (3) **Start speaking** records the mic, **Stop** ends it, and the clip is **uploaded straight to Blob** (the same `upload()` flow as the teacher recording, via `/api/quiz-audio`'s token) and then **`/api/quiz-transcribe`** is POSTed just `{blobUrl}` — it fetches the clip back, transcribes it, deletes it, and returns the text, which is appended as the student's turn and shown; (4) loop back to step 1. (The clip goes via Blob, not as a `multipart` body through the function, because a long answer exceeded Vercel's ~4.5MB request-body limit and was rejected with a **413** before the function even ran — an uncompressed iOS WAV hits 4.5MB in ~2.3 min; the direct-to-Blob path has a 50MB cap and skips the function limit.) **The very first turn is a special fast path: the opening line is a fixed script (`openingLine()` in `VoiceQuiz.tsx`, mirroring step 1 of `buildInstructions` — keep them in sync), so the client SKIPS `/api/quiz-turn` for the greeting AND does not speak it — the opening is identical every quiz and already on screen, so it's just shown and the student presses Start speaking.** Calling the chat model (with the whole article as context, plus a Blob fetch, possibly cold) just to produce a greeting we already know verbatim was the single biggest startup delay, and a redundant TTS for a fixed line was the rest — so the student now waits only on mic permission before the first turn is ready. (Because the greeting is appended to the transcript like any tutor turn, the model picks up seamlessly from turn 2 onward; from there each follow-up IS spoken via `/api/quiz-tts`.) The real `OPENAI_API_KEY` never reaches the browser (all three routes are login-gated server calls). A genuine error (couldn't transcribe / couldn't reach the tutor) **no longer ends the quiz — it PAUSES it** (`pauseOnFailure`): the failure `{reason, detail}` is recorded on the checkpointed slot, the audio-so-far is flushed best-effort, and the student gets a "We hit a snag" screen with **Try again** (`retryFromPause` re-runs the failed leg — the still-held clip for a transcription failure, the turn for a tutor failure — with fresh AbortControllers) and **Save for later** (see *Pause & resume* below). (Soft, recoverable cases — no audio captured, or a blank transcript — are *not* errors: they show an amber notice and let the student tap **Start speaking** again without pausing the session.) **The quiz ends when the student clicks the End quiz button** — the way to finish *and be graded* — but **End appears only once the tutor has signalled the quiz is complete** (the `done` flag; see *Strict End gating* below), never mid-turn. Until then the live screen shows **Start speaking** + **Save for later** + **Cancel quiz**. The tutor's wrap-up line tells them to press End ("The quiz is done. You can press the End Quiz button."). End and Cancel — the only two terminal actions — funnel through one once-guarded **`finalizeQuiz(reason)`** (`userEnd()` calls it gated on `tutorTurn && tutorDone`; `cancel()` calls it with `reason="cancel"`), so the save runs exactly once and can't be raced by a double-click; it also **drains any in-flight checkpoint** (time-capped) before saving, because the server deletes the slot right after the save and a late-landing checkpoint would resurrect a stale Continue. **A "Cancel quiz" button sits beside "End quiz" on the live screen** (`confirmCancel()`/`cancel()` in `VoiceQuiz.tsx`) and is **always available** — it's the way to stop *before* the tutor is done. Pressing it asks for confirmation (a native `confirm()` dialog — same pattern as the admin Delete; the wording separates ending-for-good from pausing: it "won't count and you won't be able to continue it later… to keep it for later, use Save for later instead"), then **saves whatever was captured so far as a `cancelled` attempt** (see *Cancelled attempts* below) rather than discarding it: `cancel()` fences stragglers, best-effort **closes out an in-flight recorder** (if the student cancelled mid-answer, that clip is stitched into the recording even though it was never transcribed — so a cancelled attempt can have a slightly longer *recording* than *transcript*), and funnels through the same **`finalizeQuiz("cancel")`** save path as End. The student sees only a brief "Ending the quiz…" holding screen and the modal **closes itself** once the save completes — **no report card** (a cancelled attempt is never graded). On End quiz (or a cancel) it POSTs the transcript to `app/api/quiz-report`, which grades it into a report card (a text model, also given the full article text — **skipped for a cancel**, which saves `score: "—"` ungraded) and saves the whole session (transcript + report + audio link + the recording's `durationMs`, **plus `partial`/`cancelled` booleans and the `failure` `{reason, detail}`** when one occurred) to **Vercel Blob** under `quiz-sessions/<date>/`; the route returns the report, and — for a normal End — the client shows the student the **full report card** — the score (e.g. "You scored 8/10"), the summary, and the **Strengths** / **To review** lists, rendered with the same layout as `/admin` — along with "saved for your teacher" and a "feel free to take the quiz again" invitation. (Only the transcript and audio recording stay teacher-only.) **After "End quiz" there is a single, stable wrap-up screen** (phase `wrapup`) — no screen-swap — with a checklist that fills in place: **Uploading your recording** → **Grading your quiz** (each a pending/active/done step with a ✓), and then, once everything is saved (`finished`), the **report card** appears below (in a scrollable block) and the **Close** button enables. **Only the student's own turns are gradable:** the report route counts the transcript's `student`-role turns and, if there are none (e.g. the student ended the quiz before speaking), it **skips the model entirely** and records an honest `score: "—"` "no answers to grade" card rather than letting the grader invent a score from the reference article. The grading prompt is also explicit that it must grade ONLY what the student actually said and never inflate a thin transcript (a previous bug let a no-speech session score 8/10). The prompt (`buildReportPrompt` in `lib/quiz-prompt.ts`) is structured for clarity — **all instructions first, then a delimited `BEGIN/END ARTICLE` section, then a delimited `BEGIN/END TRANSCRIPT` section** (no instructions interspersed with the data) — and it: tells the grader the quiz is conducted by voice (TTS + speech-to-text) so it must **not** penalize likely transcription slips (mis-hearings/homophones) as if they were real mistakes; **permits the student's relevant outside/world knowledge** — a claim is never wrong merely for being absent from the article, only if it's actually incorrect or off-topic (this fixed a real bug where a student's correct "died… aged 100", true but stated only in the article's deck/standfirst we'd failed to capture, was flagged as a weakness); and is **not given the student's name** at all, so the name can't bias the grade. The prompt also carries **calibration anchors** (`lib/grading-examples.ts`, injected as a `CALIBRATION EXAMPLES` block) plus explicit judging principles, both added because the standalone grader was found — across a week of comparative reviews — to **compress every attempt into the 8–9 band, over-reward a long/detail-packed transcript over a tighter one that actually reached the harder ideas, and drift day to day**. The anchors are a handful of **expert-revised** examples from *past* days (anonymized — no names, since the grader never sees the name), each a condensed account + the score it *should* get + the transferable principle; they span ≈6.5→9.5 so the scale is pinned top-to-bottom, and two pairs share an article (difficulty held constant) so the orderings teach the key lessons: a **long vivid retelling scores below a tighter one that reached the subtle concepts** (length ≠ depth), and a **wide-but-flawed answer scores above an accurate-but-thin one that skipped a whole major theme**. The **9.5 top-band anchor** (a complete, accurate answer that reached the article's hardest theme) is load-bearing: when re-grading the two data-center sessions live, the new prompt fixed the old grader's *inversion* (it had ranked the weaker attempt above the stronger one) but with no 9-anchor visible it bunched **both at 9**; adding the 9.5 anchor separated them to **9 vs 8.5** in the correct order — so a visible top-band example is what stops the grader collapsing strong answers into a tie. They calibrate *how* to score, not *what* today's article says (they're from other articles, never an answer key for today). Each anchor is tagged with its **`sourceDate`**, and `buildReportPrompt` passes the day being graded so `gradingExamplesBlock(reading.date)` **drops any example drawn from that same article** — an anchor must never describe (and thus pre-judge / leak the answer key for) the very transcript being graded, and it keeps the "from a different article" framing literally true (if all anchors were excluded the whole section is omitted). So on the data-center day, that day's own two anchors fall out and the grader calibrates on the World Cup + air-conditioning ones instead. The matching principles tell the grader to **count distinct correct ideas, not word count; weight reaching the article's harder/subtler ideas over restating the headline or piling on detail (a genuine conceptual error caps the score); and calibrate against THIS article's own ceiling, using the full 1–10 range rather than defaulting to 8–9**. To extend the anchor set, promote a comparative review into a new entry in `lib/grading-examples.ts`. **Leniency:** after the grader returns, the report route bumps the numeric score by **+1, clipped to 10** (`applyLeniency` in `lib/score.ts`) before the card is saved and shown — a deliberate generosity adjustment (the calibration-anchored grader scores on the strict side); the no-answers card's `"—"` is passed through untouched. The same helper was used to **back-fill historical scores** once: every saved session was re-graded through the calibration grader (single pass, like the live flow — no median) and its `report.score` (only the score, not the strengths/gaps narrative) overwritten in Blob with the new lenient value, so `/admin` shows scores consistent with how new quizzes now grade. (Overwriting a session blob in place keeps its URL; the Blob CDN edge cache can briefly serve the old copy after an overwrite but propagates within ~a minute.)
- **Strict End gating + run fencing (the 2026-06-29 data-loss fix).** The **End quiz button appears ONLY when `phase === "tutorTurn" && tutorDone`** — i.e. once the tutor has signalled completion via the `done` flag — so it can **never fire mid-turn**. This is structural: with no in-flight turn when End is allowed, End can't truncate one. (The bug it fixes: a student pressed End while her first answer was still *transcribing*; the old `end()` saved a premature 2-turn snapshot and set the once-guard but did **not** stop the turn loop, which continued through the rest of the quiz — vocab + concepts — and when the session finally hit a terminal 502 the *real* 14-turn save was **blocked by the once-guard**, losing 6 of her 7 answers. See `BUG-anusha-voice-quiz.md` + `PLAN-anusha-voice-quiz-fix.md`.) The pieces:
  - **Reliable `done`:** the tutor returns `{text, done}` JSON (see step 1 above); `done` (or the exact wrap-up phrase) is the only thing that flips `tutorDone` → reveals End and hides Start speaking. Before that, Cancel (which now saves a `cancelled` attempt — see *Cancelled attempts*) is the only way to stop.
  - **Terminal-buttons-only entry:** `end()` became **`finalizeQuiz(reason)`** — the single, once-guarded save/teardown path — reached ONLY by **`userEnd()`** (gated: `tutorTurn && tutorDone`, `reason="end-button"`) and **`cancel()`** (`reason="cancel"`). Failures/hangs no longer finalize — they **pause** (`pauseOnFailure`, see *Pause & resume*), keeping the attempt continuable. The `reason` becomes the saved `endReason`. `finalizeQuiz` needs no mid-turn reconciliation (no recorder closeout / no settle), since a user End can't fire mid-turn and cancel() closes out its own recorder — it just drains any in-flight checkpoint (see *Pause & resume*) before saving.
  - **Generation-token fencing (`activeRunIdRef`):** each quiz is one "run"; the id is bumped in `start()`/`close()`/unmount. Every async step captures its `runId` and, after each await, bails via **`canContinue(runId)`** (same run + still mounted + not terminating) — so a slow transcribe/turn/TTS from a **cancelled or unmounted** quiz can never `appendTurn`/`speak`/`setPhase` into a newer run. `turnAbortRef`/`transcribeAbortRef` (armed in `start()`) abort the in-flight `quiz-turn`/TTS and the answer upload+`quiz-transcribe` on Cancel/finalize/unmount.
  - **Backstop + fetch timeouts (so strict gating can't trap or wedge):** if the transcript passes **`MAX_TURNS` (24)** without a `done` — a runaway — the backstop **forces `tutorDone = true`** (checkpointed, `backstop:done-forced`) and shows a "ran long — press End quiz" notice, so **End appears through its normal gate** and the attempt stays finishable/gradable (pausing a runaway instead would make it permanently unfinishable — resuming a transcript already at the cap would just re-trip it); and any `quiz-turn`/`quiz-transcribe` fetch that hangs past **`FETCH_TIMEOUT_MS` (~60s)** becomes a failure → **pause** (`tutor-timeout` / `transcription-timeout`; retry-or-leave) — except the answer-clip **Blob upload** leg, whose budget scales with the clip (~60s + 30s/MB, capped at 5 min), because a long iOS answer is an uncompressed WAV (~2MB/min) and a slow-but-progressing upload on a weak uplink is not a hang. End is **never** exposed as a manual escape mid-hang — the pause screen is.
- **Pause & resume (in-progress attempts — leaving never loses a quiz; `PLAN-continue-voice-quiz.md`, Phases 1+2 shipped).** The transcript is **checkpointed after every transcribed answer and every tutor turn** (`checkpoint()` in `VoiceQuiz.tsx` → `POST /api/quiz-progress`) into a per-(student, date) **in-progress slot**: ONE Blob record at the stable key `quiz-sessions/<date>/<safeName>-inprogress.json` (safeName ALWAYS derived from the **cookie** user — the key is overwritable, so a body-derived name could stomp another student's slot), overwritten in place, shaped `{ inProgress: true, partial: true, cancelled: false, report: null, transcript, tutorDone, resumeCount, updatedAt, failure, audioUrl?, durationMs?, diag }`. The slot's existence IS the continuable state — **leaving the page / closing the modal / a reload or iOS tab-kill just pauses** (at most the last in-flight turn is lost; no unload-time work is attempted, which is exactly why checkpointing is per-answer). A **transcription/tutor failure or hang also pauses instead of ending** (`pauseOnFailure` — see *How it connects*), and while the page is still alive it **flushes the audio-so-far** to the stable slot WAV (`…-inprogress.wav` — the ONE overwritable path `/api/quiz-audio`'s token allows, and only the caller's own; the stored `audioUrl` carries a `?v=` buster), so a never-resumed failure still leaves the teacher a recording. A **"Save for later"** button (shown at `tutorTurn` and on the paused screen — never mid-recording) flushes + checkpoints and closes without ending; checkpoints with **zero student answers are never sent** (client-skipped AND server-rejected — a quiz where the student never spoke resumes identically to a fresh start). **Resuming:** the launcher probes for a slot on click and offers **Continue / Start over**; the Scores page's in-progress row gives its owner a **Continue** link → `/?resume=<date>`, which auto-resumes (read via `window.location`, not `useSearchParams` — no Suspense boundary in the static home page — and stripped after so a reload doesn't re-trigger). `resume(slot)` restores the transcript + `tutorDone`, **reuses the saved `sessionId`**, bumps `resumeCount`, arms fresh controllers, and picks the loop up (last turn = student → ask the tutor; last turn = tutor → answer it; `tutorDone` → End available immediately); the fixed-opening fast path is fresh-start only. **Only End and Cancel are terminal** — both save via `/api/quiz-report`, which **deletes the slot only after a successful save** (a storage hiccup keeps Continue alive); nothing auto-finalizes, **nothing is graded until End** (`report: null` on the slot — the grader never sees an incomplete attempt), and there is **no stale cleanup** (a slot persists until finished / cancelled / started-over, or the teacher deletes its row). **Races/staleness:** checkpoints are **serialized** and `finalizeQuiz` **drains the in-flight one** before the terminal save (a late-landing checkpoint would resurrect a stale Continue after the slot delete — client fencing can't recall a request already on the wire); every slot read (`readSlot` in `lib/session-io.ts`) forces a **CDN miss with a unique `?v=` per read**, because the slot is overwritten in place and both the Blob edge cache and `list()`'s `uploadedAt` metadata lag an overwrite (measured: origin-visible in ~1s, `list()` up to ~5s — keying by `uploadedAt` alone, the `lib/users.ts` recipe, still served stale slots), so only a leave-then-resume within a couple of seconds can miss the very last turn. **Audio is continuous across resumes (Phase 2):** `resume()` fetches the slot's flushed WAV — everything recorded up to the last flush — in the **background** (a fresh per-read cache-buster appended to the stored `?v=` URL, so the CDN can't serve an older overwrite) and prepends it to the new run's timeline as an `order:-1` "prior" segment; `buildTeacherFile` **awaits that fetch (time-capped ~10s)** before stitching, so End/Cancel/flush produce ONE recording covering every flushed run — a mid-run flush therefore rewrites the slot WAV as the *full* recording so far, and `durationMs` covers the whole thing. All best-effort: if the prior fetch fails the recording falls back to the final run only, and the End/Cancel save still **salvages the slot's flushed WAV** (copied to a permanent key in `/api/quiz-report`) when the client sent no audio at all. A run that never flushed (tab-kill — no unload-time work) still loses that run's audio; the transcript always survives via the per-answer checkpoint. `resumeCount` is stored on the final session and surfaces as a **teacher-only "Resumed N times" note** in the Details modal — pause-anytime enables a mid-quiz look-it-up detour, and the teacher gets to see an attempt didn't run in one sitting. The in-progress state is the **explicit `inProgress` flag**, deliberately NOT inferred from `partial && report == null` — **legacy** `partial` records (the old auto-graded failure-ends, incl. ones whose grading errored and saved `report: null`) still render exactly as before (amber badge + "Incomplete attempt" box) with no Continue. (Soft, recoverable hiccups — no audio captured, or a blank transcript — are *not* failures: they keep the session live with a retry notice, so a single muffled answer never pauses the quiz. `/api/quiz-transcribe` also still **retries the OpenAI call once** on a transient failure, so only a failure that survives the retry pauses.)

- **Cancelled attempts (Cancel keeps the work, teacher-only).** Pressing **Cancel quiz** no longer discards the session — it **saves whatever was recorded/transcribed so far as a `cancelled` attempt** (`cancel()` → `finalizeQuiz("cancel")` in `VoiceQuiz.tsx`, saved with `cancelled: true`). Distinct from a **pause** (leaving / a failure — which keeps the attempt continuable, see *Pause & resume*): a cancel is the student *choosing* to end early **for good** — not resumable — and is **never graded** — `app/api/quiz-report/route.ts` short-circuits the model and stores an honest `score: "—"` "Cancelled — ended early, not graded" card (so a cancel needs no `OPENAI_API_KEY` and costs nothing). The recording is still stitched + uploaded and the transcript still saved, so the teacher can hear/read how far they got; if the student cancelled **mid-answer**, that in-flight clip is closed out and included in the audio even though it was never transcribed. **`cancelled` attempts are teacher-only:** `app/admin/page.tsx` filters them out of a **student's** own Scores view (`!s.cancelled && …`) — a student never sees a cancelled entry, not even their own (they were told it "won't count") — while the **teacher sees all of them**, tagged with a grey **`cancelled` badge** in the table and a grey **"Cancelled attempt — ended early, not graded"** notice in the modal (`components/AdminSessions.tsx`). The student's own end-of-cancel UX is just a brief **"Ending the quiz…"** holding screen that closes itself once the save finishes — no checklist, no report card. The terminal save also **deletes the in-progress slot** (Cancel ends the continuable state, same as End). **"Start over"** — the launcher chooser's other option (`DELETE /api/quiz-progress`) — produces one of these `cancelled` records too: the abandoned slot is **archived** (its flushed audio copied to a permanent key; `failure.reason: "superseded"`, `diag.endReason: "start-over"`) before the slot is deleted, so nothing a student did is ever silently discarded.
- **Failures are logged with the student's name.** So a reported problem is traceable in the Vercel runtime logs (the per-turn failures carry no username otherwise): `/api/quiz-transcribe`, `/api/quiz-turn`, and `/api/quiz-report` all include the **login user** (plus the clip size/turn counts) in their `console.error` lines, and a partial save emits a distinct **`Voice-quiz partial session saved:`** line with the user, the failure reason/detail, and how far they got (student answers, total turns, whether a recording was saved).
- **Diagnostics for the split-recording bug (logging only).** A rare bug once saved **one** continuous quiz as **two** records (an Arjun attempt: a transcript-less `"—"` record holding only the long first answer's audio, plus the real `9/10` record with the rest) — and the server request logs alone couldn't reveal whether that was one quiz saving twice or a component remount. To make any recurrence self-explaining, every saved session now carries a **`diag`** object (built in `app/api/quiz-report/route.ts` from client-sent fields; all sanitized + capped): a per-quiz **`sessionId`** (one id per quiz — `resume()` REUSES the paused quiz's id, so one quiz keeps one id across pauses; two TERMINAL records with the same id ⇒ a double-save), a per-mount **`mountId`**, the **`endReason`** (`end-button` / `cancel`; a start-over archive carries `start-over`; the old `fail:<reason>` values no longer occur — failures pause instead of finalizing), the **`phaseAtEnd`**, and an ordered **`breadcrumbs`** trail (`start`, `tutor-turn:*` incl. `done=<bool>`, `start/stop-speaking` (+ `pause/resume-speaking` for the mid-answer Pause button), `transcribe:*`, `checkpoint:*`, `pause:fail/leave/retry/audio-flushed`, `resume:begin`, `backstop:done-forced`, **`end:called`** — logged for *every* `finalizeQuiz()` attempt with the live phase + once-guard state + `reason`, before the guard can bail — `end:blocked`, `save:*`). Read it on the saved record: **two terminal records with the same `sessionId` ⇒ one quiz that saved twice** (guard bypassed); **differing `mountId`s ⇒ the component remounted between saves**; **an `end:called` with `endReason="end-button"` at any `phase` other than `tutorTurn` (with `tutorDone`) ⇒ the End gate was bypassed** (alert-worthy) — whereas an `end:called` with `endReason` **`cancel`** at a non-`tutorTurn` phase is **expected** (the student cancelling mid-quiz). The breadcrumb plumbing lives under a "Diagnostics" block in `components/VoiceQuiz.tsx` (`sessionIdRef`/`mountIdRef`/`phaseRef`/`breadcrumbsRef` + a `logEvent` helper). `/api/quiz-report` also emits a concise **`Voice-quiz session saved:`** `console.log` (info, not error) on **every** save — not just partials — with the user + `sessionId`/`mountId`/`endReason`/`phaseAtEnd` + counts, so a double-save is visible in the runtime logs even if a Blob record is later deleted. (The original **split-recording / lost-answers** bug this instrumentation was built to catch has since been **fixed structurally** — see *Strict End gating* above; the diagnostics stay as a permanent tripwire for any regression.)
- **Recording the answers (per-turn for STT + one interleaved teacher file).** Each answer is recorded so it can be transcribed, and the **whole conversation — the tutor's spoken questions AND the student's answers — is stitched into ONE interleaved file for the teacher, in the order it actually happened** (so the teacher can hear which prompt each answer is responding to; previously only the student's answers were saved, which was hard to follow). The teacher file is built from an **ordered audio timeline** (`segmentsRef` / `AudioSegment` in `VoiceQuiz.tsx`): every **spoken** tutor line drops its TTS **mp3** into the timeline (in `speak()`, tagged with the tutor turn's index), and every student answer drops its clip (tagged with the slot the answer occupies). (The **opening turn is the lone exception** — it's not spoken, so it has no mp3 to add; the teacher's recording therefore starts with the student's first answer, which is fine since the opening prompt is a fixed, identical script.) At "End quiz" `buildTeacherFile()` **sorts the timeline by position, decodes every clip to mono 16 kHz PCM (`decodeBlobToPcm16k` via a throwaway `AudioContext` — `decodeAudioData` handles both the tutor's mp3 and the desktop answers' webm), concatenates, and encodes ONE seekable interleaved WAV** (`encodeWav`); a clip that won't decode is skipped best-effort. So the saved file is **always a WAV now** (both platforms), tutor-then-student-then-tutor… The per-answer *capture* path is still **platform-split** (`isIOS`), because desktop Chrome and iOS/WebKit need opposite approaches to record the student's mic — this was the single trickiest part to get working in-browser:
  - **Desktop (Chrome/Firefox):** ONE Web Audio graph owns the mic — `mic → MediaStreamSource → (a) AnalyserNode` (the live level meter) `→ (b) MediaStreamDestination`. A per-turn **`MediaRecorder` records the destination stream** (the graph's *output*, webm/opus). Recording the **raw** mic track while an AudioContext also reads the mic makes Chrome capture **silence** (a real Chromium bug — it produced 0-byte clips); recording the graph output dodges it. (Two concurrent recorders on one mic also fail, so there's exactly one.) That per-turn webm goes to Whisper and into the timeline (decoded to PCM at the end).
  - **iOS (all iOS browsers are WebKit):** `MediaRecorder` is unreliable on iOS (it also gave 0-byte clips), so iOS captures **raw PCM** via a Web Audio `ScriptProcessor` (no MediaRecorder) and **encodes a 16 kHz mono WAV in-browser** (`encodeWav`/`downsample`); that WAV goes to Whisper, and the same 16 kHz PCM goes straight into the timeline (no re-decode needed). Crucially iOS **re-acquires a fresh mic at the start of every answer** (and releases it on Stop) because iOS **mutes a long-lived `getUserMedia` track once the tutor's audio has played** through the `<audio>` element (the audio session flips to playback) — the fresh mic guarantees a live capture session. The same AnalyserNode drives the meter, so iOS gets the live meter too.
  - On "End quiz" the stitched WAV is uploaded **directly from the browser to Vercel Blob** via the `@vercel/blob` client `upload()` flow — **`app/api/quiz-audio`** only mints a short-lived, login-gated client-upload token (`handleUpload` / `onBeforeGenerateToken`, allowing `audio/webm|mp4|ogg|wav` under the `quiz-sessions/<date>/` prefix), so the bytes never pass through the serverless function and dodge Vercel's ~4.5MB request-body limit. (WAV is uncompressed, so the interleaved file is larger than the old answers-only webm — but the direct-to-Blob upload has a 50MB cap and skips the function limit, so a few minutes of speech is fine.) The returned blob URL is passed to `app/api/quiz-report` and stored as `audioUrl` on the session JSON. **The same `/api/quiz-audio` token + `upload()` flow also carries the per-turn answer clips** for transcription (under `quiz-sessions/<date>/turns/`) — `/api/quiz-transcribe` fetches each clip from Blob and then deletes it, so those transient clips don't accumulate (only the stitched teacher WAV persists). This is why both per-turn transcription and the final recording dodge the 413 the function-body path used to throw on a long answer. The whole recording path is **best-effort** — a failure to capture, upload, or save never breaks the quiz (transcript + report still save). (Recording **minors' voices** is a heavier privacy step than the transcript; the live screen discloses it.)
- **Reviewing results (the "Scores" page, `/admin`).** Every logged-in user can open it from the header **Scores** link, but **what they see is scoped to who they are**: a **teacher sees their OWN classroom's attempts** (their students' + their own — matched by the stamped `teacherId`, falling back to roster membership by `loginUser` for older sessions; **not** other teachers' students); a **student sees only their own** — the page (a server component) filters the loaded sessions **on the server**, so another classroom's/student's data never reaches the browser. **The OWNER sees every classroom in ONE unified table, split into two track tabs** — **Regular** (senior, the default) and **Junior** (`ClassroomTabs`, `ariaLabel="Reading track"`): within each tab every classroom's attempts are collapsed together, by article, newest first, with a **Teacher column** (`showTeacher`) naming whose classroom each attempt is. The old per-teacher tabs were dropped as inefficient; the track split is the only tab dimension left, so a junior 8/10 is never shown next to a senior 8/10. The owner path resolves each session's teacher display name (prefer stamped `teacherId`, fall back to roster membership by the owning student; a teacher's own attempts map to themselves), stamps it as `teacherName`, splits by track, and `groupByArticle`s each track's sessions with `canDelete` = `isOwner` (the owner may delete in any classroom). A **regular teacher** still sees just their own classroom (scoped via `scopeToClassroom`, no track tabs, no Teacher column). **Delete is owner-only:** a regular teacher views read-only (no Delete column), and only the owner gets Delete (the delete route exempts the owner from its per-classroom check). A separate `teacherView` prop (true for a teacher/owner view, false for a student's self-view) keeps the teacher-only informational bits — the "Resumed N times" note — visible to any teacher, whether or not they can delete. Across the two track tabs the unified owner view shows **every** session (including any orphan not matched to a classroom), and each session appears exactly once — in whichever track tab it belongs to. **`cancelled` attempts are additionally hidden from the student's own view** (`!s.cancelled` in the filter) — only the teacher sees them. An **in-progress attempt** (the pause-&-resume slot — it lives under the same `quiz-sessions/<date>/` prefix, so `loadSessions` lists it like any session) shows a sky **`in progress` badge**, "—" for Score and Mins, its **last-checkpoint time** (`updatedAt` — a slot has no `endedAt`; attempt ordering falls back to it), and — **for its owner** (`viewerUser` is passed down) — a **Continue** link (→ `/?resume=<date>`) in place of Details; everyone else (the teacher) gets the usual Details modal with a sky **"In progress — not yet graded"** notice (+ why it last paused, if a failure), and the **owner's** row **Delete works on the slot** (if deleted mid-quiz, the student's next checkpoint recreates it — harmless). A **"Resumed N times"** note (teacher-only, keyed off `teacherView`) shows in any attempt's modal when `resumeCount > 0`. In-progress slots are **excluded from the Students-page attempt stats** (`app/admin/students/page.tsx`). The heading reads **"Quiz sessions"** for the teacher and **"Your scores"** for a student; a logged-out visitor gets a log-in prompt instead. It presents the visible sessions as a **compact by-article table** (`components/AdminSessions.tsx`) — one row per article, newest article first, with three columns: **Date** (the article's `dateBig` label) · **Article** (its title, linked to the handout) · **Attempts**, a **sequenced (numbered) list of every (visible) attempt on that article**. Each attempt is itself a **sub-column line — Student · Score · Mins · Time · Details** (plus, in the owner's unified view, a **Teacher** column after Student naming the classroom) — and those sub-columns have **header labels** (in the table head, sharing the same fixed widths so they line up over the rows) and the data columns are **right-aligned** (plus an amber **`partial` badge** on incomplete attempts, and a grey **`cancelled` badge** on cancelled ones — the latter teacher-only, since a student's own cancelled attempts are filtered out). **Score** is shown as a **bare number** (`fmtScore` strips the `/10`, since every score is out of 10; the no-answers `—` passes through) — and it is now **plain text, not a link** (it used to be the modal's click target, styled sky-blue, but people didn't notice it was clickable). The **Details** column holds **one "Details" link** that opens the combined view-only detail modal (Feedback + Recording + Transcript together — see the file-layout note above); it's the sole click target that opens the modal (the whole-row/score-as-link affordance was replaced because it was easy to miss). For the **owner** there is then a **final Delete column** — a single per-attempt Delete (see the file-layout note above); a **regular teacher** and every **student** have no Delete column. This attempt line (the sub-columns + the Delete column, plus the owner's Teacher column) is **wider than the site-wide `max-w-3xl` reading column**, so the last column was clipping on desktop; the fix keeps the sub-columns **tight** and **widens the whole admin route** to a `max-w-5xl` column (`app/admin/layout.tsx` — widened from 4xl to fit the owner's Teacher column), with the card's `overflow-x-auto` as the fallback for narrower windows. The **duration** (`durationMs` on the session) is the **length of the saved recording** — the stitched tutor-questions + student-answers audio, i.e. the same duration the playback control shows (total talk time, not wall-clock; it excludes the gaps for reading/thinking/transcription). It's computed client-side from the stitched PCM in `buildTeacherFile` (`samples / 16000`), saved by `/api/quiz-report`, and shown as a **bare minutes number to one decimal** (the minutes unit lives in the column header — "Mins" — not on each value), e.g. "8.7" (sessions with no recording → "—"). It's part of the shared table, so **every student sees it on their own attempts**, not just the teacher. The pre-feature sessions were **backfilled once** by probing each saved recording's length (`ffprobe`, with an `ffmpeg` full-decode fallback for the older MediaRecorder `webm` clips, which carry no header duration) and writing `durationMs` back into each session JSON in Blob (overwrite-in-place, so the URL is kept) — a one-off throwaway script, not committed. **Times are shown in the viewer's local timezone** (the server runs in UTC, so the timestamp is formatted client-side after mount with a deterministic date-slice placeholder pre-mount to avoid a hydration mismatch). Clicking an attempt's **Details link pops out its full detail in a modal over the same page** — one combined view with three labeled sections: **Feedback** (score in the header + summary + strengths/gaps), **Recording** (an inline **audio player**, or "No recording saved"), and the full **Transcript** — plus, on a **partial** attempt, an amber **"Incomplete attempt — <reason>: <detail>"** notice at the top, or on a **cancelled** attempt a grey **"Cancelled attempt — ended early, not graded"** notice — the table stays compact no matter how long a transcript runs. The modal is **view-only** (no delete inside it — deleting is the single row-level action); it closes on the ✕/Close button, a backdrop click, or Esc, and locks body scroll while open. The page (`app/admin/page.tsx`, a server component) loads + parses the blobs, then **groups them by article** (using `dateBig`, which can't be imported into the client component because `lib/content` pulls in `fs`) and passes the labeled groups to the client table. The session JSON and the audio recording share the same `quiz-sessions/<date>/` prefix, so the listing **fetches only the `.json` blobs** (never tries to `JSON.parse` a `.webm`/`.mp4`/`.wav` recording), and each parse is independently guarded so one corrupt blob can't blank the page. A **teacher** is any user whose repository **`role === "teacher"`** (see **Classrooms** above); `isAdmin` derives from that (fail closed — a non-teacher sees only their own). The header **Scores** link shows for **every** logged-in user; `/api/me` returns `isAdmin`, but the link no longer gates on it. **Delete is owner-only:** the page passes `canDelete={isOwner(user)}` to the table, so the **single per-attempt Delete** (`components/DeleteSessionButton.tsx`, a red text-link in the row's Details bar — not in the modal) renders only for the owner — across the whole unified table; a regular teacher and every student see no delete at all. When shown, Delete **confirms** (a native `confirm()`), then calls `DELETE /api/quiz-session` with the session's blob URL (and its `audioUrl`) to remove the whole entry — the JSON *and* the audio — then `router.refresh()`es the list (an error surfaces via `alert()`, keeping the tight row stable).

**UI-side, Delete is owner-only** (the page passes `canDelete={isOwner(user)}`, not `isAdmin`) — a regular teacher sees no Delete column, only the owner does, across the whole unified all-classrooms table. The API route matches: it is **teacher-gated**, and the **owner may delete ANY classroom's session** (it skips the per-classroom check for an owner), while a **regular teacher is classroom-scoped** — for a non-owner it fetches the session to confirm its `teacherId`/owner belongs to the caller before `del()`ing both blobs. ## Daily vote (club pick)

The club (kids + parents — every site login) can **choose the day's article by voting** on the home page, externalizing the curation the owner used to do alone. Deliberately **skill-driven, not automated**: the owner opens the vote and reads the tally through local skills (the Claude-needing steps — scouting paywalled sites, judging candidates, authoring — stay on the owner's machine); the website only hosts the ballot box, using the logins everyone already has. The vote is **always for TODAY's read** (news can't wait a day), **per-track** (each track has its own poll: senior's on `/`, junior's on `/junior` — fully independent, one of each can be live at once; any login may vote in either), and **opt-in per day** — on a no-vote day (enrichment, or the owner just decides) nothing appears and publishing works exactly as before.

- **UX:** while a track's poll is live, the top of that track's index shows the yellow **"TODAY'S READ — YOU DECIDE"** row (`components/VotePoll.tsx`, `track` prop) in place of the usual highlighted newest entry (which is demoted to a normal row via the `vote-live` sibling-selector variants in `LandingIndex`). The row is **compact** — date · title · a muted **"N votes in"** count (the ballots-cast total — **public to everyone**, also echoed in the modal subtitle; participation, not preference) · one boxed **VOTE** button ("Voted ✓" once you have), the same shape as every other row — and the button opens the **ballot modal** (portaled, internally scrolling, phone-first), because the default senior ballot is **10 candidates — 7 news + 3 enrichment** (junior defaults to **5, news only**) — which would swamp the page inline. The modal groups them under light **"The day's news" / "Enrichment — timeless reads"** section labels (each candidate's `kind`), but it stays **ONE unified poll** — one radiogroup, one vote, one tally across all 10. Each candidate: source chip · title · a spoiler-free, non-steering 1–2-sentence pitch ending in a quiet **"(read the article)"** parenthetical link (real article links — many families subscribe; no PDF at vote stage; deliberately NOT a button — the modal is about voting, and the old boxed READ IT distracted from that); tap to select, then **Submit vote** (later **Change vote**). Login-gated on click (logged out, the modal shows a log-in prompt instead of the ballot); **one login = one vote**, equal weight, changeable while live; the **tally (counts only, never names) appears only after you've voted** (keeps the first vote un-herded). **No deadline on the site** — the owner announces the window in the group chat. There's no interim "closed" state either: the poll row simply lives until the published reading replaces it.
- **Storage & close (the seam that makes it simple):** polls live in Blob, track-prefixed like everything else junior — `votes/[junior/]<date>/poll.json` (the definition, written by `scripts/open-vote.mjs`) + `votes/[junior/]<date>/ballots/<safeName>.json`, ONE blob per voter overwritten in place to change a vote, so there are no write races and no counting state to corrupt. **"Active" is derived, never a flag** (`app/api/vote/route.ts`, track-aware — GET `?track=`, POST body `track`, default senior at the boundary): the track's newest poll is live iff no reading ON THAT TRACK exists for its date — so **publishing the day's reading is what closes that track's vote** (the deploy retires it; nothing to forget), and a poll for a never-published day is simply superseded by the next one. The senior poll listing is blind to junior polls (folding `votes/` shows them only as one dateless `votes/junior/` folder), so the two tracks never interfere. Old polls/ballots stay in Blob as a tiny permanent participation record. Ballot identity always comes from the cookie (the pathname is overwritable — a body-derived name could stomp another voter; `track` is only a label — a forged one just points at the other track's poll, which any login may vote in anyway); candidate ids are title slugs so a revised poll keeps unchanged candidates' ballots valid.
- **Workflow:** (1) **`wsj-open-vote`** — SENIOR (default): builds the ballot from BOTH pickers — the top 7 of the wsj-pick-article field (news) + the top 3 wsj-pick-enrichment picks (enrichment); JUNIOR ("open the junior vote"): the top 5 of the **wsj-pick-article-junior** field, news only. Either way it reuses a field already picked this conversation or runs the picker's workflow itself; the user approves the candidates + pitches (same manual gate as wsj-reading; counts overridable, 2–12 total), then the script posts the poll (`--track=junior` for junior) — **live immediately, no deploy**. (2) Everyone votes; the owner can peek anytime with **`wsj-check-vote`** (tally WITH voter names — owner-side only; checking never closes the poll; `--track=junior` for the junior poll). (3) The user runs **`wsj-reading`** (senior) / **`wsj-reading-junior`** (junior) with the winner — it sets **`clubPick: true`** (the permanent **CLUB PICK** chip on the row) and its publish closes that track's poll. **Ties/vetoes are the owner's silent call** — the vote is advisory by construction, and the site never claims "the winner was X".

## Daily workflow

Two picking skills feed one authoring skill, with the user as the validation layer between them. The **picking step has two flavors** — pick whichever the user asks for (or both): `wsj-pick-article` for the day's **news**, `wsj-pick-enrichment` for a **timeless-wisdom** read (the junior track has its own news picker, `wsj-pick-article-junior` — see the JUNIOR paragraph below). Either one just recommends; the user chooses a link and step 2 builds it. On a **vote day**, the club chooses instead: `wsj-open-vote` (after the picking) puts the candidates up for a vote on that track's index and `wsj-check-vote` reads the winner back — see the **Daily vote** section; the winning link then feeds step 2 as usual (with `clubPick: true`).

1. **`wsj-pick-article`** — run first each day ("pick an article", "what should we read today"). Checks `content/` for recently covered domains (quality, learning value, and articulation quality come first, with a **standing lean toward worldly wisdom — general knowledge, finance, and modern forces like AI**, which are welcome to recur; variety across days is only a mild tiebreaker, never a quota), browses **both the wsj.com and economist.com homepages** (pooling candidates across the two sources — the source is just a label on each pick; **if either site looks logged-out or paywalled it stops and asks the user to log in** before continuing, since The Economist hard-paywalls logged-out readers), verifies candidates are substantive text articles you can read in full (not video-led pages, live blogs, or chart-only stubs), and recommends a ranked top pick plus 2–3 runners-up. It only recommends — the **user** checks the suggestions and picks one.

   **1b. `wsj-pick-enrichment`** — the alternative first step ("pick an enrichment article", "a wisdom read", "a mental-models piece"). Instead of the day's news it proposes **five** timeless-wisdom candidates from a broader, mostly-free source pool (Farnam Street, Our World in Data, short Paul Graham + the wider tiers; **Morgan Housel is permanently excluded** — owner's standing rule). Same reading-club fit gates as `wsj-pick-article`, plus a **HARD ≤2,000-word rule** (~1,000 typical), a positive-tone bias, and a "teach a transferable Munger mental model" aim; timeless beats timely, and it excludes URLs already used in `content/`. It fills the gap the news sources leave — **mental models taught as models** — and is the layer where the club's *worldly-wisdom* goal is met directly (the AI/news weight stays on `wsj-pick-article`). Recommends only; the user picks one and step 2 builds it. (Origin: the 2026-07-14 "enrichment sources" discussion.)
2. **`wsj-reading`** — invoked with the chosen link (or when the user pastes any WSJ link / says "today's reading"). It reads the article in the browser (the user logs into WSJ themselves), then **proposes the vocab words (3 by default, overridable) and up to 3 concepts (as many strong transferable ideas as the article supports, capped at 3 — fewer, even 0, is fine; overridable) and waits for the user's explicit go-ahead before generating anything** (a manual quality gate — the selection is discussed and revised first), writes `content/YYYY-MM-DD.json` (with `voiceQuiz: true` so the day's voice quiz is live), **captures the day's PDF from the open page** (→ `public/pdfs/YYYY-MM-DD.pdf`, setting `pdfUrl`; the `PDFs/` drop-zone is now only a manual fallback) — built by **rebuilding a clean doc from the article's own text *plus its real content images* (charts/graphs/photos)** and printing *that*, rather than running `page.pdf()` on the live DOM. It extracts the article's `<p>`/heading text in document order — **preserving the original inline typography** (small-caps acronyms, italics, bold, the drop-cap opening) — and interleaves only its genuine figures — each fetched at a sensible ~1000px width (not the 5000px `srcset` monster), inlined as a `data:` URI, height-capped to one page, and stopping at the end-of-article footer so related-article thumbnails/ads are excluded. Printing the live page instead bloated the file to tens of MB (full-`srcset` photos + leftover `<video>` posters and empty ad slots) and **sliced lines of text in half at page breaks**; the rebuild lands at ~150–500KB with images embedded and paginates cleanly. **(It used to strip images entirely — text-only — which dropped critical charts/graphs; it now keeps them.)** **(It also used to flatten text with `innerText`, which silently lowercased the Economist's small-caps acronyms — "AI"→"ai", "IBM"→"ibm" — and split the drop cap; it now reads raw text nodes and re-applies small-caps via `font-variant-caps`, so acronym case is retained in both the PDF and the `pdftotext` output used by the voice quiz.)** The SKILL.md has the exact snippet — **uploads the full article text to Blob** (`pdftotext` → `scripts/upload-article-text.mjs`, so the tutor gets the whole article), **generates the handout's pronunciation clips** (`scripts/gen-pronunciation.mjs` → `public/audio/<date>/`, committed, so each vocab word/concept name gets its ▶ audio) — then builds, commits, and pushes (which deploys).

Audience calibration lives in both skills; the article-first content rules live in `.claude/skills/wsj-reading/SKILL.md`. Hard rule: link to WSJ and quote only short phrases — never republish the article text.

**The JUNIOR track (`wsj-reading-junior`).** The occasional grades-5–7 track (see the "Tracks" subsection under Architecture) has its **own authoring skill**, invoked when the user says "junior reading" / "add a junior article" / gives a link for the junior track. It's a **track-adapted sibling** of `wsj-reading`: same two-step flow (read the article in the browser → propose vocab + concepts → wait for sign-off → generate) and the same PDF/audio/article-text machinery, but with **(a) a grades-5–7 audience calibration** (simpler-but-real vocabulary; concepts kept *even more* concrete — the Feynman hook→how-it-works→example rule matters more, not less — and capped at **the 2 most important concepts** by default, NOT the senior 3–5: two ideas taught deeply beat four taught thinly at this age), **(b) the `junior/` output paths** everywhere (`content/junior/<date>.json`, `public/pdfs/junior/`, `article-text/junior/` and `public/audio/junior/` via the two scripts' `--track=junior` flag), and **(c) the user supplies the link** — pasted directly, chosen from **`wsj-pick-article-junior`** (the junior news picker — grade 5–7 calibration: story-first, the 11-year-old prerequisite gate, junior-register vocab, coverage check on `content/junior/`), or the **junior vote's** winner (in which case it sets `clubPick: true`, and its publish closes the junior poll). It publishes to `/junior/reading/<date>`. The skill references the senior skill's exact PDF-capture snippet (only the `OUT` path differs) rather than duplicating it, so the fragile snippet stays single-source. **Grading strictness is unchanged** — only the audience *band* swaps (see the Voice-quiz grader notes); expect junior scores to read low at first until real junior transcripts exist to calibrate anchors from.

## Deploy

GitHub `cosmic-glitch/wsj_club` (public) → Vercel project `wsj_club` (team *Anurag's projects*). **Push to `main` auto-deploys to production** at `wsjclub.vercel.app` — no manual `vercel --prod` needed. `npm run build` validates every content JSON locally.

**Env vars** (for the voice quiz — set in Vercel project settings, and locally in the gitignored `.env.local`): `OPENAI_API_KEY` (required), `AUTH_USERS` (base64 bcrypt logins — see Voice quiz above; no login works without it), `AUTH_SECRET` (a long random string), `OWNER_USERS` (comma-separated owner usernames — an owner is a teacher who may also create teachers; fail closed), `ADMIN_USERS` + `AUTH_USERS` (now only a **transitional fallback** for logins not yet migrated into the Blob user repository — see **Classrooms**/**Auth gates it**; removable once the seed is confirmed), `BLOB_READ_WRITE_TOKEN` (auto-added when a Vercel Blob store is linked; `vercel env pull` to get it locally), and optionally the voice-quiz model knobs `TUTOR_MODEL`, `TTS_MODEL`, `TTS_VOICE`, `STT_MODEL`, `REPORT_MODEL` (see *Models/voice* above). The voice quiz is inert (returns a clean error) until `OPENAI_API_KEY` is set; saving to Blob is best-effort and won't break a session if `BLOB_READ_WRITE_TOKEN` is missing.

**Already provisioned in Vercel** — no need to re-do setup: `OPENAI_API_KEY`, `AUTH_USERS`, and `AUTH_SECRET` are set for **Production + Preview** (marked *sensitive*, so they're intentionally absent from the Development scope and from `vercel env pull`), and a linked Blob store **`wsj-club-quizzes`** supplies `BLOB_READ_WRITE_TOKEN` to all environments. The working copies also live in the local gitignored `.env.local`. `ADMIN_USERS` is **provisioned to `anurag`** (Production + Preview, and in `.env.local`), so `/admin` is unlocked for that teacher login; admin is additive, so `anurag` is also a normal `AUTH_USERS` login who can take the voice quiz. The other logins (`anusha`, `samaira`, `arjun`, `mehar`) are students — voice quiz only. (To change teachers, edit the comma-separated `ADMIN_USERS` in both scopes and `.env.local`, then redeploy.) `OWNER_USERS` is **provisioned to `anurag`** (Production + Preview, and in `.env.local`) — this is what makes `isOwner("anurag")` true so the owner sees every classroom on the Scores + Manage Students pages (and may Delete attempts in any classroom on Scores, and Add a student to any classroom on Manage Students; Rename/Reset there stay own-classroom). **It fails closed: an unset `OWNER_USERS` in an environment silently downgrades the owner to a plain teacher** (seeing only their own classroom) — this bit once (the var lived only in `.env.local`, never in Vercel, so the owner-classrooms feature looked broken in prod until it was added). An env-var-only change like this needs a **redeploy** (`vercel --prod`) to take effect — pushing code isn't required, but existing deployments don't pick up new env vars. For a fresh checkout, recreate `.env.local` by hand (the sensitive values aren't pullable) — at minimum `OPENAI_API_KEY`, `AUTH_SECRET`, an `AUTH_USERS` from the hash script, `ADMIN_USERS`, `OWNER_USERS`, and `BLOB_READ_WRITE_TOKEN` (pullable via `vercel env pull`).

## Blob backups (cron, Hetzner VM)

The Blob store (`wsj-club-quizzes` — users, quiz sessions + teacher recordings, votes, article text) is backed up daily to the Hetzner VM (`myhetzner`), the same box that runs the foliotracker crons, where this repo lives at `~/wsj_club`.

- **Script:** `scripts/backup-blob.sh` (sources `.env.local`, `flock`s, 30-day retention prune) wraps `scripts/backup-blob.mjs` (`@vercel/blob` `list()` with cursor pagination → download each blob).
- **Snapshots:** `backups/<YYYY-MM-DD>/<pathname>` + a `manifest.json` (pathname/size/uploadedAt/url — the restore map; written last, so its presence marks a snapshot complete). Gitignored, VM-only.
- **Incremental:** files whose size + `uploadedAt` match the previous snapshot's manifest are **hardlinked** from it instead of re-downloaded (rsync `--link-dest` semantics), so 30 dated snapshots cost ~one copy of the store plus deltas, and a normal run takes seconds. Downloads carry a `?v=` cache-buster because overwritten-in-place blobs (slots/users/votes) lag in the Blob edge cache.
- **Crontab (on the VM):** `15 6 * * * $HOME/wsj_club/scripts/backup-blob.sh >> $HOME/wsj_club/backups/backup.log 2>&1` — daily, slotted between foliotracker's 05:50 news and 06:30 DB-backup jobs.
- **Caveats:** backups live only on the VM (append an `rclone`/S3 push to the wrapper for off-box durability), and daily granularity means a same-day Blob deletion can lose up to a day. Transient `quiz-sessions/*/turns/` clips are deleted after transcription, so their absence from a snapshot is normal.
