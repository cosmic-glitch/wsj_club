# WSJ Reading Club

A daily reading-handout website for a small club of four kids in US grades 8–10. Each day = one Wall Street Journal article turned into a study handout with two sections — **Words to know** and **Concepts behind the story** — plus a **self-quiz** on its own page. Goal: build general knowledge, vocabulary, and conceptual understanding.

Live: https://wsjclub.vercel.app · Repo: https://github.com/cosmic-glitch/wsj_club

## Architecture

Next.js app (App Router, Next 16, React 19, Tailwind v4). The daily content is **data, not code**: one JSON file per day in `content/`. The content pages (index, handout, quiz) are **statically generated** — adding a day = adding one JSON file. The **voice-quiz feature** (see below) adds a handful of **dynamic server routes** (login, per-turn tutor/TTS/transcribe, audio-upload token, report card) and an admin page, so the app is no longer purely static, but every content page still prerenders.

## Content schema (`lib/content.ts`)

A `Reading` = `{ date, title, articleUrl?, pdfUrl?, articles?, voiceQuiz?, source?, vocab[], concepts[], quiz[] }`.

- **articleUrl** — the WSJ web article (the **Web** link). **pdfUrl** (optional) — a served PDF of the article, e.g. `/pdfs/2026-06-09.pdf` (the **PDF** link); omit it and only the Web link shows.
- **voiceQuiz** (optional `boolean`) — when `true`, the home-page row for that day shows the AI-oral-quiz launcher in its action bar **to everyone** (signed in or not); clicking it while logged out pops a login prompt instead of starting. The skill sets `voiceQuiz: true` on every new day. It is now set on **every day** — the earlier pre-feature days (2026-06-09 → 2026-06-17) were backfilled, so all entries have the voice quiz for logged-in users.
- **articles** (optional) — for **multi-article days**: bundle two or more short articles into one combined handout. It's an array of `Source` = `{ title, articleUrl, pdfUrl? }` (each article's own headline + links). When `articles` is set, the top-level `articleUrl`/`pdfUrl` are unused, the vocab/concepts/quiz are **combined** across all the articles, and each article gets its own PDF named `/pdfs/YYYY-MM-DD-1.pdf`, `-2.pdf`, … (see `content/2026-06-14.json` for the first one). Most days are single-article and just use `articleUrl`.

- **vocab** — exactly **3** `VocabWord`s, each presented *article-first*:
  `articleQuote` (short real quote from the article) → `inContext` (what it means there) → `meaning` (broader definition) → `examples` (exactly **2** more example sentences).
- **concepts** — 3–5 `Concept`s, same article-first shape:
  `articleQuote` → `inContext` → `meaning` (how it actually works). **May be empty (`[]`) for a vocabulary-only day** — when an article is vocab-rich but thin on transferable concepts, it's better to drop the section than to ship weak, topic-bound concepts. An empty `concepts` is handled everywhere: the handout **omits the "Concepts behind the story" section** (and drops the lone step-number on the words section), and the voice quiz **skips its concepts stage** — `buildInstructions`/`buildReportPrompt` in `lib/quiz-prompt.ts` branch on `concepts.length` so the tutor never quizzes (and the grader never penalizes) concepts that don't exist. The first such day is `content/2026-06-24.json`. Most days still run 3–5 concepts.
- **quiz** — exactly **5** `QuizQuestion`s, each `{ question, options (4), answerIndex (0-based), explanation }`.

Pages stay minimal. The **index** is a **compact row-list, one row per day** (a `<ul>` inside a single bordered card, hairline `divide-y` between rows, newest first). It replaced the earlier tall "one box per day" cards: those were ~8 lines each and scrolled badly as the list grows. The design intent was a **table**, but a literal `<table>` was rejected — a table shares column widths across all rows, so one long headline squeezes the action columns and forces **horizontal scroll on a phone** (the same problem that had earlier killed a six-column table). The row-list gets table-like compactness *without* that: each row's action bar simply **wraps** to a second line on narrow screens instead of scrolling. Each row is the **date** (a muted serif label, `dateBig`) + the **article title** as plain text (**not** a link) on one prominent line, then a small **action bar** of text links separated by middots (`·`): **Web link** — the mobile-aware `ArticleLink` — then a separate **PDF** link (its own middot-separated item, **not** a parenthetical "(PDF)") when `pdfUrl` is set; multi-article days (when `articles` is set) show "Web link 1 · PDF 1 · Web link 2 · PDF 2 · …", one numbered pair per source; then **Handout**; then **Voice quiz** (shown to everyone — see below). The separating middots carry generous horizontal margins (`mx-2.5`) so each action reads as a distinct, separately tappable target with clear breathing room on a phone, where the bar wraps. There is **no self-quiz and no 1-1-quiz (Calendly) link on the index** anymore — the self-quiz moved to a CTA at the **bottom of each handout** (`/reading/<date>/quiz`, every day has one), and the Calendly 1-1-quiz link was dropped from the index entirely (it is no longer linked anywhere). The **Voice quiz** is a small client component, `components/VoiceQuizStep.tsx`: it's one more middot-separated action-bar item that **brings its own leading `·`** and is shown to **everyone**, signed in or not (it shows for any day with `voiceQuiz: true`). The login check happens **on click**, inside `VoiceQuiz`'s `launch()`: a signed-out visitor who clicks it gets a "You need to log in" popup instead of starting a session, so the public can see the feature but can't run up OpenAI charges. (Login state is still fetched **once** for the whole page by `AuthProvider` — a client context wrapped around the app in `app/layout.tsx`, which the header `AuthControl` and each `VoiceQuiz`'s click-handler read from — not per row; before that, every day's `VoiceQuizStep`+`VoiceQuiz` and the header `AuthControl` each fetched `/api/me` independently, so on a logged-in home page a dozen-plus identical requests fired.) (The launcher button in `VoiceQuiz.tsx` is styled as a text link so it sits inline in the bar.) The handout top is **just the article title** (no date), then the two sections, then the **"Take the self-quiz →" CTA**. **Navigation is deliberately sparse:** the WSJ article link lives only on the index (in each row's action bar), and the only "← All readings" link is the one in the global header bar (`app/layout.tsx`, rendered via `components/AllReadingsLink.tsx`, which **hides it on the home page** — where it's redundant — and shows it on every other page) — content pages (handout, quiz) carry no inline back-link of their own. No summary/blurb, no reading-time estimate. In both vocab and concept cards the quote is labeled **"Quote from the article"**, followed by **"What it means here"** (in the article) and **"In general"** (the broader meaning).

## Voice quiz (beta)

A "Voice quiz" feature that automates the teacher's 1-1 oral quiz: a student clicks the **Voice quiz** link in that day's row on the home page and an AI tutor quizzes them aloud about that day's article in a modal, then a report card is generated and saved. It runs **turn by turn, fully under the student's control** — the tutor's question appears on screen and is spoken aloud (OpenAI **TTS**; the fixed opening turn is shown but **not** spoken, only later follow-ups are), the student presses **Start speaking** to record their answer and **Stop** when done (a state toggle, not press-and-hold), the answer is transcribed (OpenAI **speech-to-text**) and shown on screen, and a **chat model** decides the next question — repeating until the student presses **End quiz**. There is **no realtime/WebRTC speech-to-speech session and no model-driven turn detection** (an earlier build used OpenAI's Realtime API with `semantic_vad`; letting the model guess when the student had finished was unreliable, so turn-taking moved to explicit buttons). **At the end the student is shown their full report card** — the same score + summary + strengths/gaps the teacher sees on `/admin` — plus an invitation to retake the quiz if they're not happy with it. The student now also **sees their own transcribed answers** as they go (and the tutor's questions); the full transcript and the **audio recording stay private (teacher-only)** and are captured to Blob for review on `/admin` (the live screen tells the student their answers are recorded). The **voice-quiz action is shown to everyone** — signed in or not (`components/VoiceQuizStep.tsx`) — for any day with `voiceQuiz: true`, and it is the **last item in the day's action bar** ("Web link · PDF · Handout · Voice quiz"). The login gate is **on click**: clicking the voice quiz while logged out pops up a "You need to log in" message rather than starting, so the public can see the feature but can't run up OpenAI charges without logging in.

- **Auth gates it.** The whole site is public to browse, but starting a quiz requires login (a header **Log in** control). This is what stops the public from running up OpenAI charges. Credentials live in the `AUTH_USERS` env var: **base64-encoded JSON `{ username: bcryptHash }`**. Passwords are stored only as **bcrypt hashes** (bcryptjs, 10 salt rounds — same scheme as the foliotracker project), never plaintext, never in source; if `AUTH_USERS` is unset there are no users and **nobody can log in (fail closed)**. (Base64 because bcrypt hashes contain `$`, which Next's `.env` loader would expand.) Generate/extend the value with `node scripts/hash-password.mjs <user> <password> …` and set it as the env var. Login sets a signed httpOnly cookie (HMAC with `AUTH_SECRET`). To onboard the four real students, just regenerate `AUTH_USERS` with their names/passwords — no code change. `lib/auth.ts` is the auth core; `app/api/login|logout|me`.
- **The flow** (`lib/quiz-prompt.ts`, `buildInstructions`): a short **opening** turn — just "Hi <name>" (it does **not** name the article, since the title is already on screen) plus the first task ("explain the key ideas, as much as you remember, bring in as many layers as you can; take your time, pauses/ums are fine"). The opening line is a fixed script, **identical every quiz and already on screen, so it is NOT spoken** — the student just reads it and presses Start speaking; **only the tutor's later, dynamic follow-ups are spoken** (kept short on purpose so their TTS is quick). The **recording mechanics are also NOT spoken** — they're shown on screen as a small helper line under the Start speaking button (`RecordingHelp` in `VoiceQuiz.tsx`: "press **Start speaking**, wait until it shows **Recording**, then talk; press **Stop** when done; same for every question"), visible on every turn → the student's from-memory **key ideas** retelling, which the tutor **listens to without interrupting** and then **judges generously** (no nitpicking, no expecting every detail; it just checks they covered a good number of the article's real ideas and went **beyond the obvious title**). The bar is a good reading by a typical 8th–10th grader (not a perfect summary): if the retelling clears it, the tutor **moves on with NO follow-up at all**; only if it was clearly wrong or significantly lacking does the tutor ask **exactly ONE broad, thematic follow-up** (about the big picture / main point — never a narrow hunt for a specific name, number, or event), and then **moves on regardless of how that answer went** — a remaining gap just lowers the score, it never earns a second question (no repeated back-and-forth). **At the end of the key-ideas round, if an area was weak the tutor gives a brief "educational update" (a one-or-two-sentence mini-lesson, a statement not a question) before moving on** → **vocabulary** (meaning or use-in-a-sentence for each of the 3 words) → a few **concepts** from the handout → short encouraging wrap-up that ends by telling the student, word for word, "The quiz is done. You can press the End Quiz button." (the student then clicks **End quiz** to close — there is no auto-end). The day's vocab/concept *meanings* are injected as the tutor's answer key. A high-level **style guide** (Socratic, one question at a time, hint-don't-reveal, stay on-article, **patient listening — never interrupt**, and **"coach the gaps"** on the **words and concepts** — whenever the student is wrong or half-right there, **ask a guiding follow-up question first** and only *tell* them the correct version if they still don't get it after that; the **key-ideas round is the exception** — at most ONE broad follow-up, then move on) lives in `STYLE_GUIDE` in that file — tune it there.
- **Full article text (the tutor's reference).** When available, the tutor is given the **whole article as plain text** (plus the full handout), so on the key-ideas step it *listens to the student's entire from-memory retelling without interrupting*, then judges it against the real story — accepting imperfect recall but expecting a few non-obvious points beyond the headline, and only probing afterward. The text is **not committed** (CLAUDE.md hard rule: never republish article text); it lives in **Vercel Blob** at `article-text/<date>.txt` (`lib/article-text.ts` reads it; `getArticleText` returns null → handout-only fallback for days without it). Upload it with `pdftotext public/pdfs/<date>.pdf article-text/<date>.txt` then `node --env-file=.env.local scripts/upload-article-text.mjs <date>` (the `/article-text/` dir is a gitignored drop-zone). This upload is now **part of the wsj-reading skill** (step 3), so every new day gets it. The earlier days were all backfilled too — from their captured PDFs (06-09/10/11/12/15/17, plus the two-article 06-14 concatenated), the Paul Graham essay page (06-13), and the original economist.com article (06-16, fetched with the user logged in, since its `archive.ph` link is CAPTCHA-walled). So **every day has full article text** in Blob.
- **Turn-taking is button-driven, never inferred.** The student decides when each of their turns starts and ends by pressing **Start speaking** / **Stop**, so the tutor can never cut in (the whole point of moving off the realtime model). This makes the patient-listening rule structural rather than a model setting: the long key-ideas retelling simply runs as long as the student holds the floor. The trade-off is latency — after **Stop**, the turn does **transcribe → next-question → TTS** sequentially (~3–6s of "Transcribing… / Thinking…"), which is fine for a quiz and far cheaper than per-minute realtime. The live screen shows explicit status for each of those steps.
- **How it connects.** `components/VoiceQuiz.tsx` (client) renders the **Voice quiz** launcher (a link-styled button) as the home-page row's voice-quiz action-bar item (wrapped by `components/VoiceQuizStep.tsx`, which just supplies the leading middot — the launcher shows for everyone). It reads login state from the shared `AuthProvider` context (one `/api/me` fetch for the whole page; login/logout reload the page, so it stays fresh) and gates on click: logged out → a "You need to log in" modal; logged in → it opens the modal, grabs the mic (the click is the user gesture that also lets audio play), and uses the **login username** as the student name. The quiz then runs as a **turn loop** managed by a `phase` state machine (`starting → tutorTurn → recording → transcribing → thinking → …`, plus `wrapup`/`error`): (1) **`/api/quiz-turn`** is POSTed the running transcript and returns the tutor's next line — its system prompt is `buildInstructions` with the day's full article text pulled from Blob, so the chat model judges answers against the real story; (2) the line is shown in an on-screen conversation log and spoken via **`/api/quiz-tts`** (mp3 played through a hidden `<audio>`; best-effort — if TTS fails the student just reads it) — **except the opening turn, which is shown but not spoken** (see the fast path below); (3) **Start speaking** records the mic, **Stop** ends it, and the clip is **uploaded straight to Blob** (the same `upload()` flow as the teacher recording, via `/api/quiz-audio`'s token) and then **`/api/quiz-transcribe`** is POSTed just `{blobUrl}` — it fetches the clip back, transcribes it, deletes it, and returns the text, which is appended as the student's turn and shown; (4) loop back to step 1. (The clip goes via Blob, not as a `multipart` body through the function, because a long answer exceeded Vercel's ~4.5MB request-body limit and was rejected with a **413** before the function even ran — an uncompressed iOS WAV hits 4.5MB in ~2.3 min; the direct-to-Blob path has a 50MB cap and skips the function limit.) **The very first turn is a special fast path: the opening line is a fixed script (`openingLine()` in `VoiceQuiz.tsx`, mirroring step 1 of `buildInstructions` — keep them in sync), so the client SKIPS `/api/quiz-turn` for the greeting AND does not speak it — the opening is identical every quiz and already on screen, so it's just shown and the student presses Start speaking.** Calling the chat model (with the whole article as context, plus a Blob fetch, possibly cold) just to produce a greeting we already know verbatim was the single biggest startup delay, and a redundant TTS for a fixed line was the rest — so the student now waits only on mic permission before the first turn is ready. (Because the greeting is appended to the transcript like any tutor turn, the model picks up seamlessly from turn 2 onward; from there each follow-up IS spoken via `/api/quiz-tts`.) The real `OPENAI_API_KEY` never reaches the browser (all three routes are login-gated server calls). A genuine error (couldn't transcribe / couldn't reach the tutor) is recorded as a session **failure** (`failureRef` / `recordFailure`) and **immediately ends the quiz** via `failAndEnd`, saving the attempt as a **partial** (see *Partial attempts* below) **automatically — no button press**. (Soft, recoverable cases — no audio captured, or a blank transcript — are *not* errors: they show an amber notice and let the student tap **Start speaking** again without ending the session.) **The quiz ends when the student clicks the End quiz button** — the way to finish *and be graded*. The tutor's wrap-up line tells them to press it ("The quiz is done. You can press the End Quiz button."); a once-guard makes `end()` idempotent against a double-click. **A "Cancel quiz" button sits beside "End quiz" on the live screen** (`cancel()` in `VoiceQuiz.tsx`): it abandons the session with **nothing saved** — no recording, no transcript, no session JSON — straight back to idle (it sets the once-guard so a racing `end()` can't fire). Cancel is **always a clean discard** now that errors auto-save-and-end on their own (the earlier "Save & exit" variant of this button is gone — there's no live session left to bail out of after a failure). On End quiz (or an automatic end after a failure) it POSTs the transcript to `app/api/quiz-report`, which grades it into a report card (a text model, also given the full article text) and saves the whole session (transcript + report + audio link + the quiz `durationMs`, **plus a `partial` boolean and the `failure` `{reason, detail}`** when one occurred) to **Vercel Blob** under `quiz-sessions/<date>/`; the route returns the report, and the client shows the student the **full report card** — the score (e.g. "You scored 8/10"), the summary, and the **Strengths** / **To review** lists, rendered with the same layout as `/admin` — along with "saved for your teacher" and a "feel free to take the quiz again" invitation. (Only the transcript and audio recording stay teacher-only.) **After "End quiz" there is a single, stable wrap-up screen** (phase `wrapup`) — no screen-swap — with a checklist that fills in place: **Uploading your recording** → **Grading your quiz** (each a pending/active/done step with a ✓), and then, once everything is saved (`finished`), the **report card** appears below (in a scrollable block) and the **Close** button enables. **Only the student's own turns are gradable:** the report route counts the transcript's `student`-role turns and, if there are none (e.g. the student ended the quiz before speaking), it **skips the model entirely** and records an honest `score: "—"` "no answers to grade" card rather than letting the grader invent a score from the reference article. The grading prompt is also explicit that it must grade ONLY what the student actually said and never inflate a thin transcript (a previous bug let a no-speech session score 8/10). The prompt (`buildReportPrompt` in `lib/quiz-prompt.ts`) is structured for clarity — **all instructions first, then a delimited `BEGIN/END ARTICLE` section, then a delimited `BEGIN/END TRANSCRIPT` section** (no instructions interspersed with the data) — and it: tells the grader the quiz is conducted by voice (TTS + speech-to-text) so it must **not** penalize likely transcription slips (mis-hearings/homophones) as if they were real mistakes; **permits the student's relevant outside/world knowledge** — a claim is never wrong merely for being absent from the article, only if it's actually incorrect or off-topic (this fixed a real bug where a student's correct "died… aged 100", true but stated only in the article's deck/standfirst we'd failed to capture, was flagged as a weakness); and is **not given the student's name** at all, so the name can't bias the grade. The prompt also carries **calibration anchors** (`lib/grading-examples.ts`, injected as a `CALIBRATION EXAMPLES` block) plus explicit judging principles, both added because the standalone grader was found — across a week of comparative reviews — to **compress every attempt into the 8–9 band, over-reward a long/detail-packed transcript over a tighter one that actually reached the harder ideas, and drift day to day**. The anchors are a handful of **expert-revised** examples from *past* days (anonymized — no names, since the grader never sees the name), each a condensed account + the score it *should* get + the transferable principle; they span ≈6.5→9.5 so the scale is pinned top-to-bottom, and two pairs share an article (difficulty held constant) so the orderings teach the key lessons: a **long vivid retelling scores below a tighter one that reached the subtle concepts** (length ≠ depth), and a **wide-but-flawed answer scores above an accurate-but-thin one that skipped a whole major theme**. The **9.5 top-band anchor** (a complete, accurate answer that reached the article's hardest theme) is load-bearing: when re-grading the two data-center sessions live, the new prompt fixed the old grader's *inversion* (it had ranked the weaker attempt above the stronger one) but with no 9-anchor visible it bunched **both at 9**; adding the 9.5 anchor separated them to **9 vs 8.5** in the correct order — so a visible top-band example is what stops the grader collapsing strong answers into a tie. They calibrate *how* to score, not *what* today's article says (they're from other articles, never an answer key for today). Each anchor is tagged with its **`sourceDate`**, and `buildReportPrompt` passes the day being graded so `gradingExamplesBlock(reading.date)` **drops any example drawn from that same article** — an anchor must never describe (and thus pre-judge / leak the answer key for) the very transcript being graded, and it keeps the "from a different article" framing literally true (if all anchors were excluded the whole section is omitted). So on the data-center day, that day's own two anchors fall out and the grader calibrates on the World Cup + air-conditioning ones instead. The matching principles tell the grader to **count distinct correct ideas, not word count; weight reaching the article's harder/subtler ideas over restating the headline or piling on detail (a genuine conceptual error caps the score); and calibrate against THIS article's own ceiling, using the full 1–10 range rather than defaulting to 8–9**. To extend the anchor set, promote a comparative review into a new entry in `lib/grading-examples.ts`. **Leniency:** after the grader returns, the report route bumps the numeric score by **+1, clipped to 10** (`applyLeniency` in `lib/score.ts`) before the card is saved and shown — a deliberate generosity adjustment (the calibration-anchored grader scores on the strict side); the no-answers card's `"—"` is passed through untouched. The same helper was used to **back-fill historical scores** once: every saved session was re-graded through the calibration grader (single pass, like the live flow — no median) and its `report.score` (only the score, not the strengths/gaps narrative) overwritten in Blob with the new lenient value, so `/admin` shows scores consistent with how new quizzes now grade. (Overwriting a session blob in place keeps its URL; the Blob CDN edge cache can briefly serve the old copy after an overwrite but propagates within ~a minute.)
- **Partial attempts (don't lose a failed recording).** If a **transcription or tutor-turn failure** happens during a quiz, the quiz **ends itself immediately and saves the attempt as a partial** — `failAndEnd` in `VoiceQuiz.tsx` records the failure and calls the normal `end()` save flow with `partial: true`, **with no button press** — because the answer's audio is captured client-side *before* transcription runs, so the recording usually exists even when transcription fails. The failure `{reason, detail}` is recorded on `failureRef` (e.g. `transcription-failed` · "Couldn't transcribe answer 3 (server returned 502)") and stored on the session. A **clean** session is unaffected: **Cancel quiz** discards with nothing saved, and a completed quiz saves with `partial: false`. The student's wrap-up screen reflects it — heading flips to **"Saved — we hit a snag"** with a message that it was saved incomplete and they can retake. `/admin` shows a **`partial` badge** on the attempt and an amber **"Incomplete attempt — <reason>: <detail>"** box in its modal. (Soft, recoverable hiccups — no audio captured, or a blank transcript — are *not* treated as failures: they keep the session live with a retry notice, so a single muffled answer never ends the quiz.)
- **Failures are logged with the student's name.** So a reported problem is traceable in the Vercel runtime logs (the per-turn failures carry no username otherwise): `/api/quiz-transcribe`, `/api/quiz-turn`, and `/api/quiz-report` all include the **login user** (plus the clip size/turn counts) in their `console.error` lines, and a partial save emits a distinct **`Voice-quiz partial session saved:`** line with the user, the failure reason/detail, and how far they got (student answers, total turns, whether a recording was saved).
- **Recording the answers (per-turn for STT + one interleaved teacher file).** Each answer is recorded so it can be transcribed, and the **whole conversation — the tutor's spoken questions AND the student's answers — is stitched into ONE interleaved file for the teacher, in the order it actually happened** (so the teacher can hear which prompt each answer is responding to; previously only the student's answers were saved, which was hard to follow). The teacher file is built from an **ordered audio timeline** (`segmentsRef` / `AudioSegment` in `VoiceQuiz.tsx`): every **spoken** tutor line drops its TTS **mp3** into the timeline (in `speak()`, tagged with the tutor turn's index), and every student answer drops its clip (tagged with the slot the answer occupies). (The **opening turn is the lone exception** — it's not spoken, so it has no mp3 to add; the teacher's recording therefore starts with the student's first answer, which is fine since the opening prompt is a fixed, identical script.) At "End quiz" `buildTeacherFile()` **sorts the timeline by position, decodes every clip to mono 16 kHz PCM (`decodeBlobToPcm16k` via a throwaway `AudioContext` — `decodeAudioData` handles both the tutor's mp3 and the desktop answers' webm), concatenates, and encodes ONE seekable interleaved WAV** (`encodeWav`); a clip that won't decode is skipped best-effort. So the saved file is **always a WAV now** (both platforms), tutor-then-student-then-tutor… The per-answer *capture* path is still **platform-split** (`isIOS`), because desktop Chrome and iOS/WebKit need opposite approaches to record the student's mic — this was the single trickiest part to get working in-browser:
  - **Desktop (Chrome/Firefox):** ONE Web Audio graph owns the mic — `mic → MediaStreamSource → (a) AnalyserNode` (the live level meter) `→ (b) MediaStreamDestination`. A per-turn **`MediaRecorder` records the destination stream** (the graph's *output*, webm/opus). Recording the **raw** mic track while an AudioContext also reads the mic makes Chrome capture **silence** (a real Chromium bug — it produced 0-byte clips); recording the graph output dodges it. (Two concurrent recorders on one mic also fail, so there's exactly one.) That per-turn webm goes to Whisper and into the timeline (decoded to PCM at the end).
  - **iOS (all iOS browsers are WebKit):** `MediaRecorder` is unreliable on iOS (it also gave 0-byte clips), so iOS captures **raw PCM** via a Web Audio `ScriptProcessor` (no MediaRecorder) and **encodes a 16 kHz mono WAV in-browser** (`encodeWav`/`downsample`); that WAV goes to Whisper, and the same 16 kHz PCM goes straight into the timeline (no re-decode needed). Crucially iOS **re-acquires a fresh mic at the start of every answer** (and releases it on Stop) because iOS **mutes a long-lived `getUserMedia` track once the tutor's audio has played** through the `<audio>` element (the audio session flips to playback) — the fresh mic guarantees a live capture session. The same AnalyserNode drives the meter, so iOS gets the live meter too.
  - On "End quiz" the stitched WAV is uploaded **directly from the browser to Vercel Blob** via the `@vercel/blob` client `upload()` flow — **`app/api/quiz-audio`** only mints a short-lived, login-gated client-upload token (`handleUpload` / `onBeforeGenerateToken`, allowing `audio/webm|mp4|ogg|wav` under the `quiz-sessions/<date>/` prefix), so the bytes never pass through the serverless function and dodge Vercel's ~4.5MB request-body limit. (WAV is uncompressed, so the interleaved file is larger than the old answers-only webm — but the direct-to-Blob upload has a 50MB cap and skips the function limit, so a few minutes of speech is fine.) The returned blob URL is passed to `app/api/quiz-report` and stored as `audioUrl` on the session JSON. **The same `/api/quiz-audio` token + `upload()` flow also carries the per-turn answer clips** for transcription (under `quiz-sessions/<date>/turns/`) — `/api/quiz-transcribe` fetches each clip from Blob and then deletes it, so those transient clips don't accumulate (only the stitched teacher WAV persists). This is why both per-turn transcription and the final recording dodge the 413 the function-body path used to throw on a long answer. The whole recording path is **best-effort** — a failure to capture, upload, or save never breaks the quiz (transcript + report still save). (Recording **minors' voices** is a heavier privacy step than the transcript; the live screen discloses it.)
- **Reviewing results (the "Scores" page, `/admin`).** Every logged-in user can open it from the header **Scores** link, but **what they see is scoped to who they are**: the **teacher (an `ADMIN_USERS` login) sees ALL students' attempts**; a **student sees only their own** — the page (a server component) filters the loaded sessions by `loginUser` (falling back to `studentName`) **on the server**, so another student's data never reaches the browser. The heading reads **"Quiz sessions"** for the teacher and **"Your scores"** for a student; a logged-out visitor gets a log-in prompt instead. It presents the visible sessions as a **compact by-article table** (`components/AdminSessions.tsx`) — one row per article, newest article first, with three columns: **Date** (the article's `dateBig` label) · **Article** (its title, linked to the handout) · **Attempts**, a **sequenced (numbered) list of every (visible) attempt on that article**, each showing the **student name · the score · the duration · the local-time timestamp** (plus an amber **`partial` badge** on incomplete attempts). The **duration** (`durationMs` on the session) is how long the quiz actually took — measured client-side from the first question to "End quiz" (so it excludes upload + grading), saved by `/api/quiz-report`, and formatted as e.g. "4m 32s" (older sessions predate it → "—"); it's part of the shared table, so **every student sees it on their own attempts**, not just the teacher. **Times are shown in the viewer's local timezone** (the server runs in UTC, so the timestamp is formatted client-side after mount with a deterministic date-slice placeholder pre-mount to avoid a hydration mismatch). Clicking an attempt **pops out its full detail in a modal over the same page** (score, summary, strengths/gaps, an inline **audio player** when a recording was saved, and the full transcript — plus, on a **partial** attempt, an amber **"Incomplete attempt — <reason>: <detail>"** notice at the top) — the table stays compact no matter how long a transcript runs. The modal closes on the ✕/Close button, a backdrop click, or Esc, and locks body scroll while open. The page (`app/admin/page.tsx`, a server component) loads + parses the blobs, then **groups them by article** (using `dateBig`, which can't be imported into the client component because `lib/content` pulls in `fs`) and passes the labeled groups to the client table. The session JSON and the audio recording share the same `quiz-sessions/<date>/` prefix, so the listing **fetches only the `.json` blobs** (never tries to `JSON.parse` a `.webm`/`.mp4`/`.wav` recording), and each parse is independently guarded so one corrupt blob can't blank the page. The **teacher** is whoever is listed in the **`ADMIN_USERS`** env var (comma-separated usernames; each must also be a login in `AUTH_USERS`); if `ADMIN_USERS` is unset, **nobody is a teacher (fail closed)** so everyone sees only their own — the page still works, just student-scoped for all. The header **Scores** link now shows for **every** logged-in user (not just admins); `/api/me` still returns `isAdmin`, but the link no longer gates on it. Onboard yourself as the teacher by adding your username to both `AUTH_USERS` (via `scripts/hash-password.mjs`) and `ADMIN_USERS`. **Delete is teacher-only:** the page passes `canDelete={isAdmin}` to the table, so the per-attempt **Delete** button (`components/DeleteSessionButton.tsx`) renders only for the teacher; a student's modal is read-only (just Close). When shown, Delete confirms, then calls `DELETE /api/quiz-session` with the session's blob URL (and its `audioUrl`), `router.refresh()`es the list, and (via the `onDeleted` callback) closes the modal. That route is **admin-gated** and `del()`s both blobs, refusing any URL not under the `quiz-sessions/` prefix; the page attaches each JSON blob's `url` as `blobUrl` at load time (it isn't part of the saved session JSON).
- **Models/voice** are env-overridable in case OpenAI renames them: `TUTOR_MODEL` (default `gpt-5.4-mini` — the chat model that drives `/api/quiz-turn`; same family as the grader, set to `gpt-5.4` for stronger Socratic judgment), `TTS_MODEL` (default `gpt-4o-mini-tts` — the current quality TTS model; it accepts a tone `instructions` string, which the route sends only for the `gpt-4o` family), `TTS_VOICE` (default `onyx` — a warm, deep male voice echoing the old realtime "cedar"; other voices: `alloy`/`echo`/`fable`/`onyx` male-ish, `nova`/`shimmer`/`coral`/`sage` female-ish, `ash`/`ballad`/`verse`), `STT_MODEL` (default `whisper-1` — robust speech-to-text for `/api/quiz-transcribe`; overridable to `gpt-4o-transcribe`/`gpt-4o-mini-transcribe`), and `REPORT_MODEL` (default `gpt-5.5` — the grader; the strongest model, chosen for the richest report-card feedback; verified working with our chat/completions + `response_format: json_object` request this build; override to `gpt-5.4`/`gpt-5.4-mini` for a cheaper grade — at ~3.2¢ vs ~0.4¢ per grading, 5.5 is ~8.5× the cost but volume is a handful of gradings a day, so still negligible). ## Daily workflow

Two skills, two steps, with the user as the validation layer between them:

1. **`wsj-pick-article`** — run first each day ("pick an article", "what should we read today"). Checks `content/` for recently covered domains (quality and learning value come first; variety across days is a preference, used as a tiebreaker), browses **both the wsj.com and economist.com homepages** (pooling candidates across the two sources — the source is just a label on each pick; **if either site looks logged-out or paywalled it stops and asks the user to log in** before continuing, since The Economist hard-paywalls logged-out readers), verifies candidates are substantive text articles you can read in full (not video-led pages, live blogs, or chart-only stubs), and recommends a ranked top pick plus 2–3 runners-up. It only recommends — the **user** checks the suggestions and picks one.
2. **`wsj-reading`** — invoked with the chosen link (or when the user pastes any WSJ link / says "today's reading"). It reads the article in the browser (the user logs into WSJ themselves), then **proposes the 3 vocab words and 3–5 concepts and waits for the user's explicit go-ahead before generating anything** (a manual quality gate — the selection is discussed and revised first), writes `content/YYYY-MM-DD.json` (with `voiceQuiz: true` so the day's voice quiz is live), **captures the day's PDF from the open page** (→ `public/pdfs/YYYY-MM-DD.pdf`, setting `pdfUrl`; the `PDFs/` drop-zone is now only a manual fallback) — built by **rebuilding a clean doc from the article's own text *plus its real content images* (charts/graphs/photos)** and printing *that*, rather than running `page.pdf()` on the live DOM. It extracts the article's `<p>`/heading text in document order and interleaves only its genuine figures — each fetched at a sensible ~1000px width (not the 5000px `srcset` monster), inlined as a `data:` URI, height-capped to one page, and stopping at the end-of-article footer so related-article thumbnails/ads are excluded. Printing the live page instead bloated the file to tens of MB (full-`srcset` photos + leftover `<video>` posters and empty ad slots) and **sliced lines of text in half at page breaks**; the rebuild lands at ~150–500KB with images embedded and paginates cleanly. **(It used to strip images entirely — text-only — which dropped critical charts/graphs; it now keeps them.)** The SKILL.md has the exact snippet — **uploads the full article text to Blob** (`pdftotext` → `scripts/upload-article-text.mjs`, so the tutor gets the whole article) — then builds, commits, and pushes (which deploys).

Audience calibration lives in both skills; the article-first content rules live in `.claude/skills/wsj-reading/SKILL.md`. Hard rule: link to WSJ and quote only short phrases — never republish the article text.
