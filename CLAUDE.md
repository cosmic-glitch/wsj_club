# WSJ Reading Club

A daily reading-handout website for a small club of four kids in US grades 8–10. Each day = one Wall Street Journal article turned into a study handout with two sections — **Words to know** and **Concepts behind the story** — plus a **self-quiz** on its own page. Goal: build general knowledge, vocabulary, and conceptual understanding.

Live: https://wsjclub.vercel.app · Repo: https://github.com/cosmic-glitch/wsj_club

## Architecture

Next.js app (App Router, Next 16, React 19, Tailwind v4). The daily content is **data, not code**: one JSON file per day in `content/`. The content pages (index, handout, quiz) are **statically generated** — adding a day = adding one JSON file. The **voice-quiz feature** (see below) adds a handful of **dynamic server routes** (login, per-turn tutor/TTS/transcribe, audio-upload token, report card) and an admin page, so the app is no longer purely static, but every content page still prerenders.


## Content schema (`lib/content.ts`)

A `Reading` = `{ date, title, articleUrl?, pdfUrl?, articles?, voiceQuiz?, source?, vocab[], concepts[], quiz[] }`.

- **articleUrl** — the WSJ web article (the **Web** link). **pdfUrl** (optional) — a served PDF of the article, e.g. `/pdfs/2026-06-09.pdf` (the **PDF** link); omit it and only the Web link shows.
- **voiceQuiz** (optional `boolean`) — when `true`, the home-page row for that day shows the AI-oral-quiz launcher in its action bar **to everyone** (signed in or not); clicking it while logged out pops a login prompt instead of starting. The skill sets `voiceQuiz: true` on every new day. It is now set on **every day** — the earlier pre-feature days (2026-06-09 → 2026-06-17) were backfilled, so all entries have the voice quiz for logged-in users.
- **articles** (optional) — for **multi-article days**: bundle two or more short articles into one combined handout. It's an array of `Source` = `{ title, articleUrl, pdfUrl? }` (each article's own headline + links). When `articles` is set, the top-level `articleUrl`/`pdfUrl` are unused, the vocab/concepts/quiz are **combined** across all the articles, and each article gets its own PDF named `/pdfs/YYYY-MM-DD-1.pdf`, `-2.pdf`, … (see `content/2026-06-14.json` for the first one). Most days are single-article and just use `articleUrl`.

- **vocab** — exactly **3** `VocabWord`s, each presented *article-first*:
  `articleQuote` (short real quote from the article) → `inContext` (what it means there) → `meaning` (broader definition) → `examples` (exactly **2** more example sentences).
- **concepts** — 3–5 `Concept`s, same article-first shape:
  `articleQuote` → `inContext` → `meaning` (how it actually works).
- **quiz** — exactly **5** `QuizQuestion`s, each `{ question, options (4), answerIndex (0-based), explanation }`.

Pages stay minimal. The **index** is a **compact row-list, one row per day** (a `<ul>` inside a single bordered card, hairline `divide-y` between rows, newest first). It replaced the earlier tall "one box per day" cards: those were ~8 lines each and scrolled badly as the list grows. The design intent was a **table**, but a literal `<table>` was rejected — a table shares column widths across all rows, so one long headline squeezes the action columns and forces **horizontal scroll on a phone** (the same problem that had earlier killed a six-column table). The row-list gets table-like compactness *without* that: each row's action bar simply **wraps** to a second line on narrow screens instead of scrolling. Each row is the **date** (a muted serif label, `dateBig`) + the **article title** as plain text (**not** a link) on one prominent line, then a small **action bar** of text links separated by middots (`·`): **Web link** — the mobile-aware `ArticleLink` — then a separate **PDF** link (its own middot-separated item, **not** a parenthetical "(PDF)") when `pdfUrl` is set; multi-article days (when `articles` is set) show "Web link 1 · PDF 1 · Web link 2 · PDF 2 · …", one numbered pair per source; then **Handout**; then **Voice quiz** (shown to everyone — see below). The separating middots carry generous horizontal margins (`mx-2.5`) so each action reads as a distinct, separately tappable target with clear breathing room on a phone, where the bar wraps. There is **no self-quiz and no 1-1-quiz (Calendly) link on the index** anymore — the self-quiz moved to a CTA at the **bottom of each handout** (`/reading/<date>/quiz`, every day has one), and the Calendly 1-1-quiz link was dropped from the index entirely (it is no longer linked anywhere). The **Voice quiz** is a small client component, `components/VoiceQuizStep.tsx`: it's one more middot-separated action-bar item that **brings its own leading `·`** and is shown to **everyone**, signed in or not (it shows for any day with `voiceQuiz: true`). The login check happens **on click**, inside `VoiceQuiz`'s `launch()`: a signed-out visitor who clicks it gets a "You need to log in" popup instead of starting a session, so the public can see the feature but can't run up OpenAI charges. (Login state is still fetched **once** for the whole page by `AuthProvider` — a client context wrapped around the app in `app/layout.tsx`, which the header `AuthControl` and each `VoiceQuiz`'s click-handler read from — not per row; before that, every day's `VoiceQuizStep`+`VoiceQuiz` and the header `AuthControl` each fetched `/api/me` independently, so on a logged-in home page a dozen-plus identical requests fired.) (The launcher button in `VoiceQuiz.tsx` is styled as a text link so it sits inline in the bar.) The handout top is **just the article title** (no date), then the two sections, then the **"Take the self-quiz →" CTA**. **Navigation is deliberately sparse:** the WSJ article link lives only on the index (in each row's action bar), and the only "← All readings" link is the one in the global header bar (`app/layout.tsx`, rendered via `components/AllReadingsLink.tsx`, which **hides it on the home page** — where it's redundant — and shows it on every other page) — content pages (handout, quiz) carry no inline back-link of their own. No summary/blurb, no reading-time estimate. In both vocab and concept cards the quote is labeled **"Quote from the article"**, followed by **"What it means here"** (in the article) and **"In general"** (the broader meaning).

## Voice quiz (beta)

A "Voice quiz" feature that automates the teacher's 1-1 oral quiz: a student clicks the **Voice quiz** link in that day's row on the home page and an AI tutor quizzes them aloud about that day's article in a modal, then a report card is generated and saved. It runs **turn by turn, fully under the student's control** — the tutor speaks a question (OpenAI **TTS**), the student presses **Start speaking** to record their answer and **Stop** when done (a state toggle, not press-and-hold), the answer is transcribed (OpenAI **speech-to-text**) and shown on screen, and a **chat model** decides the next question — repeating until the student presses **End quiz**. There is **no realtime/WebRTC speech-to-speech session and no model-driven turn detection** (an earlier build used OpenAI's Realtime API with `semantic_vad`; letting the model guess when the student had finished was unreliable, so turn-taking moved to explicit buttons). **At the end the student is shown their full report card** — the same score + summary + strengths/gaps the teacher sees on `/admin` — plus an invitation to retake the quiz if they're not happy with it. The student now also **sees their own transcribed answers** as they go (and the tutor's questions); the full transcript and the **audio recording stay private (teacher-only)** and are captured to Blob for review on `/admin` (the live screen tells the student their answers are recorded). The **voice-quiz action is shown to everyone** — signed in or not (`components/VoiceQuizStep.tsx`) — for any day with `voiceQuiz: true`, and it is the **last item in the day's action bar** ("Web link · PDF · Handout · Voice quiz"). The login gate is **on click**: clicking the voice quiz while logged out pops up a "You need to log in" message rather than starting, so the public can see the feature but can't run up OpenAI charges without logging in.

- **Auth gates it.** The whole site is public to browse, but starting a quiz requires login (a header **Log in** control). This is what stops the public from running up OpenAI charges. Credentials live in the `AUTH_USERS` env var: **base64-encoded JSON `{ username: bcryptHash }`**. Passwords are stored only as **bcrypt hashes** (bcryptjs, 10 salt rounds — same scheme as the foliotracker project), never plaintext, never in source; if `AUTH_USERS` is unset there are no users and **nobody can log in (fail closed)**. (Base64 because bcrypt hashes contain `$`, which Next's `.env` loader would expand.) Generate/extend the value with `node scripts/hash-password.mjs <user> <password> …` and set it as the env var. Login sets a signed httpOnly cookie (HMAC with `AUTH_SECRET`). To onboard the four real students, just regenerate `AUTH_USERS` with their names/passwords — no code change. `lib/auth.ts` is the auth core; `app/api/login|logout|me`.
- **The flow** (`lib/quiz-prompt.ts`, `buildInstructions`): a combined **opening** turn — just "Hi <name>" (it does **not** name the article, since the title is already on screen), then in one breath the first task plus how recording works ("explain the key ideas, as much as you remember, bring in as many layers as you can; take your time, pauses/ums are fine; press **Start speaking**, wait until it shows recording started, then talk; press **Stop** when done; do the same for every later question" — the button mechanics are explained **once**) → the student's from-memory **key ideas** retelling, which the tutor **listens to without interrupting** and then **judges generously** (no nitpicking, no expecting every detail; it just checks they covered a good number of the article's real ideas and went **beyond the obvious title**). If the answer is good enough the tutor **moves on without follow-ups**; only if it was too shallow does it ask one or two more. **At the end of the key-ideas round, if an area was weak the tutor gives a brief "educational update" (a one-or-two-sentence mini-lesson) before moving on** → **vocabulary** (meaning or use-in-a-sentence for each of the 3 words) → a few **concepts** from the handout → short encouraging wrap-up that ends by telling the student, word for word, "The quiz is done. You can press the End Quiz button." (the student then clicks **End quiz** to close — there is no auto-end). The day's vocab/concept *meanings* are injected as the tutor's answer key. A high-level **style guide** (Socratic, one question at a time, hint-don't-reveal, stay on-article, **patient listening — never interrupt**, and **"coach the gaps"** — whenever the student is wrong or half-right on an idea/word/concept, **ask a guiding follow-up question first** and only *tell* them the correct version if they still don't get it after that) lives in `STYLE_GUIDE` in that file — tune it there.
- **Full article text (the tutor's reference).** When available, the tutor is given the **whole article as plain text** (plus the full handout), so on the key-ideas step it *listens to the student's entire from-memory retelling without interrupting*, then judges it against the real story — accepting imperfect recall but expecting a few non-obvious points beyond the headline, and only probing afterward. The text is **not committed** (CLAUDE.md hard rule: never republish article text); it lives in **Vercel Blob** at `article-text/<date>.txt` (`lib/article-text.ts` reads it; `getArticleText` returns null → handout-only fallback for days without it). Upload it with `pdftotext public/pdfs/<date>.pdf article-text/<date>.txt` then `node --env-file=.env.local scripts/upload-article-text.mjs <date>` (the `/article-text/` dir is a gitignored drop-zone). This upload is now **part of the wsj-reading skill** (step 3), so every new day gets it. The earlier days were all backfilled too — from their captured PDFs (06-09/10/11/12/15/17, plus the two-article 06-14 concatenated), the Paul Graham essay page (06-13), and the original economist.com article (06-16, fetched with the user logged in, since its `archive.ph` link is CAPTCHA-walled). So **every day has full article text** in Blob.
- **Turn-taking is button-driven, never inferred.** The student decides when each of their turns starts and ends by pressing **Start speaking** / **Stop**, so the tutor can never cut in (the whole point of moving off the realtime model). This makes the patient-listening rule structural rather than a model setting: the long key-ideas retelling simply runs as long as the student holds the floor. The trade-off is latency — after **Stop**, the turn does **transcribe → next-question → TTS** sequentially (~3–6s of "Transcribing… / Thinking…"), which is fine for a quiz and far cheaper than per-minute realtime. The live screen shows explicit status for each of those steps.
- **How it connects.** `components/VoiceQuiz.tsx` (client) renders the **Voice quiz** launcher (a link-styled button) as the home-page row's voice-quiz action-bar item (wrapped by `components/VoiceQuizStep.tsx`, which just supplies the leading middot — the launcher shows for everyone). It reads login state from the shared `AuthProvider` context (one `/api/me` fetch for the whole page; login/logout reload the page, so it stays fresh) and gates on click: logged out → a "You need to log in" modal; logged in → it opens the modal, grabs the mic (the click is the user gesture that also lets audio play), and uses the **login username** as the student name. The quiz then runs as a **turn loop** managed by a `phase` state machine (`starting → tutorTurn → recording → transcribing → thinking → …`, plus `wrapup`/`error`): (1) **`/api/quiz-turn`** is POSTed the running transcript and returns the tutor's next line — its system prompt is `buildInstructions` with the day's full article text pulled from Blob, so the chat model judges answers against the real story; (2) the line is shown in an on-screen conversation log and spoken via **`/api/quiz-tts`** (mp3 played through a hidden `<audio>`; best-effort — if TTS fails the student just reads it); (3) **Start speaking** records the mic, **Stop** ends it, and the clip is sent to **`/api/quiz-transcribe`**, whose returned text is appended as the student's turn and shown; (4) loop back to step 1. The real `OPENAI_API_KEY` never reaches the browser (all three routes are login-gated server calls). A transient miss (couldn't transcribe / couldn't reach the tutor) shows an amber notice and a retry path without dropping the session. **The quiz ends when the student clicks the End quiz button** — the only way to finish *and be graded*. The tutor's wrap-up line tells them to press it ("The quiz is done. You can press the End Quiz button."); a once-guard makes `end()` idempotent against a double-click. **A "Cancel quiz" button always sits beside "End quiz" on the live screen** (`cancel()` in `VoiceQuiz.tsx`): it abandons the session with **nothing saved** — no recording uploaded, no transcript graded, no session JSON written — tearing everything down straight back to idle (it also sets the once-guard so a racing `end()` can't fire). On End quiz it POSTs the transcript to `app/api/quiz-report`, which grades it into a report card (a text model, also given the full article text) and saves the whole session (transcript + report + audio link) to **Vercel Blob** under `quiz-sessions/<date>/`; the route returns the report, and the client shows the student the **full report card** — the score (e.g. "You scored 8/10"), the summary, and the **Strengths** / **To review** lists, rendered with the same layout as `/admin` — along with "saved for your teacher" and a "feel free to take the quiz again" invitation. (Only the transcript and audio recording stay teacher-only.) **After "End quiz" there is a single, stable wrap-up screen** (phase `wrapup`) — no screen-swap — with a checklist that fills in place: **Uploading your recording** → **Grading your quiz** (each a pending/active/done step with a ✓), and then, once everything is saved (`finished`), the **report card** appears below (in a scrollable block) and the **Close** button enables. **Only the student's own turns are gradable:** the report route counts the transcript's `student`-role turns and, if there are none (e.g. the student ended the quiz before speaking), it **skips the model entirely** and records an honest `score: "—"` "no answers to grade" card rather than letting the grader invent a score from the reference article. The grading prompt is also explicit that it must grade ONLY what the student actually said and never inflate a thin transcript (a previous bug let a no-speech session score 8/10).
- **Recording the answers (per-turn for STT + one interleaved teacher file).** Each answer is recorded so it can be transcribed, and the **whole conversation — the tutor's spoken questions AND the student's answers — is stitched into ONE interleaved file for the teacher, in the order it actually happened** (so the teacher can hear which prompt each answer is responding to; previously only the student's answers were saved, which was hard to follow). The teacher file is built from an **ordered audio timeline** (`segmentsRef` / `AudioSegment` in `VoiceQuiz.tsx`): every tutor line drops its TTS **mp3** into the timeline (in `speak()`, tagged with the tutor turn's index), and every student answer drops its clip (tagged with the slot the answer occupies). At "End quiz" `buildTeacherFile()` **sorts the timeline by position, decodes every clip to mono 16 kHz PCM (`decodeBlobToPcm16k` via a throwaway `AudioContext` — `decodeAudioData` handles both the tutor's mp3 and the desktop answers' webm), concatenates, and encodes ONE seekable interleaved WAV** (`encodeWav`); a clip that won't decode is skipped best-effort. So the saved file is **always a WAV now** (both platforms), tutor-then-student-then-tutor… The per-answer *capture* path is still **platform-split** (`isIOS`), because desktop Chrome and iOS/WebKit need opposite approaches to record the student's mic — this was the single trickiest part to get working in-browser:
  - **Desktop (Chrome/Firefox):** ONE Web Audio graph owns the mic — `mic → MediaStreamSource → (a) AnalyserNode` (the live level meter) `→ (b) MediaStreamDestination`. A per-turn **`MediaRecorder` records the destination stream** (the graph's *output*, webm/opus). Recording the **raw** mic track while an AudioContext also reads the mic makes Chrome capture **silence** (a real Chromium bug — it produced 0-byte clips); recording the graph output dodges it. (Two concurrent recorders on one mic also fail, so there's exactly one.) That per-turn webm goes to Whisper and into the timeline (decoded to PCM at the end).
  - **iOS (all iOS browsers are WebKit):** `MediaRecorder` is unreliable on iOS (it also gave 0-byte clips), so iOS captures **raw PCM** via a Web Audio `ScriptProcessor` (no MediaRecorder) and **encodes a 16 kHz mono WAV in-browser** (`encodeWav`/`downsample`); that WAV goes to Whisper, and the same 16 kHz PCM goes straight into the timeline (no re-decode needed). Crucially iOS **re-acquires a fresh mic at the start of every answer** (and releases it on Stop) because iOS **mutes a long-lived `getUserMedia` track once the tutor's audio has played** through the `<audio>` element (the audio session flips to playback) — the fresh mic guarantees a live capture session. The same AnalyserNode drives the meter, so iOS gets the live meter too.
  - On "End quiz" the stitched WAV is uploaded **directly from the browser to Vercel Blob** via the `@vercel/blob` client `upload()` flow — **`app/api/quiz-audio`** only mints a short-lived, login-gated client-upload token (`handleUpload` / `onBeforeGenerateToken`, allowing `audio/webm|mp4|ogg|wav`), so the bytes never pass through the serverless function and dodge Vercel's ~4.5MB request-body limit. (WAV is uncompressed, so the interleaved file is larger than the old answers-only webm — but the direct-to-Blob upload has a 50MB cap and skips the function limit, so a few minutes of speech is fine.) The returned blob URL is passed to `app/api/quiz-report` and stored as `audioUrl` on the session JSON. The whole recording path is **best-effort** — a failure to capture, upload, or save never breaks the quiz (transcript + report still save). (Recording **minors' voices** is a heavier privacy step than the transcript; the live screen discloses it.)
- **Reviewing results (teacher-only).** `/admin` presents the saved sessions as a **compact by-article table** (`components/AdminSessions.tsx`) — one row per article, newest article first, with three columns: **Date** (the article's `dateBig` label) · **Article** (its title, linked to the handout) · **Attempts**, a **sequenced (numbered) list of every attempt on that article across all students**, each showing the **student name · the local-time timestamp · the score**. **Times are shown in the viewer's local timezone** (the server runs in UTC, so the timestamp is formatted client-side after mount with a deterministic date-slice placeholder pre-mount to avoid a hydration mismatch). Clicking an attempt **pops out its full detail in a modal over the same page** (score, summary, strengths/gaps, an inline **audio player** when a recording was saved, and the full transcript) — the table stays compact no matter how long a transcript runs. The modal closes on the ✕/Close button, a backdrop click, or Esc, and locks body scroll while open. The page (`app/admin/page.tsx`, a server component) loads + parses the blobs, then **groups them by article** (using `dateBig`, which can't be imported into the client component because `lib/content` pulls in `fs`) and passes the labeled groups to the client table. The session JSON and the audio recording share the same `quiz-sessions/<date>/` prefix, so the listing **fetches only the `.json` blobs** (never tries to `JSON.parse` a `.webm`/`.mp4`/`.wav` recording), and each parse is independently guarded so one corrupt blob can't blank the page. It's gated to teachers by the **`ADMIN_USERS`** env var (comma-separated usernames; each must also be a login in `AUTH_USERS`). If `ADMIN_USERS` is unset, **nobody is an admin (fail closed)** — students who log in for the voice quiz can't reach it. An **Admin** link appears in the header only for admins (`/api/me` returns `isAdmin`). Onboard yourself by adding your username to both `AUTH_USERS` (via `scripts/hash-password.mjs`) and `ADMIN_USERS`. Each attempt's modal has a **Delete** button (`components/DeleteSessionButton.tsx`) that confirms, then calls `DELETE /api/quiz-session` with the session's blob URL (and its `audioUrl`), `router.refresh()`es the list, and (via the `onDeleted` callback) closes the modal. The route is **admin-gated** and `del()`s both blobs, refusing any URL not under the `quiz-sessions/` prefix; the page attaches each JSON blob's `url` as `blobUrl` at load time (it isn't part of the saved session JSON).
- **Models/voice** are env-overridable in case OpenAI renames them: `TUTOR_MODEL` (default `gpt-5.4-mini` — the chat model that drives `/api/quiz-turn`; same family as the grader, set to `gpt-5.4` for stronger Socratic judgment), `TTS_MODEL` (default `gpt-4o-mini-tts` — the current quality TTS model; it accepts a tone `instructions` string, which the route sends only for the `gpt-4o` family), `TTS_VOICE` (default `onyx` — a warm, deep male voice echoing the old realtime "cedar"; other voices: `alloy`/`echo`/`fable`/`onyx` male-ish, `nova`/`shimmer`/`coral`/`sage` female-ish, `ash`/`ballad`/`verse`), `STT_MODEL` (default `whisper-1` — robust speech-to-text for `/api/quiz-transcribe`; overridable to `gpt-4o-transcribe`/`gpt-4o-mini-transcribe`), and `REPORT_MODEL` (default `gpt-5.4-mini` — the grader; verified working with our chat/completions + `response_format: json_object` request this build; set `REPORT_MODEL=gpt-5.4` for the full model). Volume is tiny — a few short utterances/transcripts a day — so cost is negligible. **Delivery (tone, pace, warmth) is steered through the tutor's instructions** (`STYLE_GUIDE`) plus the TTS tone `instructions`, not a separate speed knob; **no voice cloning** (can't use a custom/your-own voice). The realtime-only vars (`REALTIME_MODEL`/`REALTIME_VOICE`/`REALTIME_VAD_EAGERNESS`) are **gone** — they no longer do anything.

## Daily workflow

Two skills, two steps, with the user as the validation layer between them:

1. **`wsj-pick-article`** — run first each day ("pick an article", "what should we read today"). Checks `content/` for recently covered domains (quality and learning value come first; variety across days is a preference, used as a tiebreaker), browses **both the wsj.com and economist.com homepages** (pooling candidates across the two sources — the source is just a label on each pick; **if either site looks logged-out or paywalled it stops and asks the user to log in** before continuing, since The Economist hard-paywalls logged-out readers), verifies candidates are substantive text articles you can read in full (not video-led pages, live blogs, or chart-only stubs), and recommends a ranked top pick plus 2–3 runners-up. It only recommends — the **user** checks the suggestions and picks one.
2. **`wsj-reading`** — invoked with the chosen link (or when the user pastes any WSJ link / says "today's reading"). It reads the article in the browser (the user logs into WSJ themselves), then **proposes the 3 vocab words and 3–5 concepts and waits for the user's explicit go-ahead before generating anything** (a manual quality gate — the selection is discussed and revised first), writes `content/YYYY-MM-DD.json` (with `voiceQuiz: true` so the day's voice quiz is live), **captures the day's PDF directly from the open page** (`page.pdf()` → `public/pdfs/YYYY-MM-DD.pdf`, setting `pdfUrl`; the `PDFs/` drop-zone is now only a manual fallback) — capturing **text-focused** (isolate the `<article>`, drop images, `printBackground:false`) so the file stays ~100KB rather than tens of MB, because Chromium's print path otherwise embeds every photo at full `srcset` resolution (the SKILL.md has the exact snippet) — **uploads the full article text to Blob** (`pdftotext` → `scripts/upload-article-text.mjs`, so the tutor gets the whole article) — then builds, commits, and pushes (which deploys).

Audience calibration lives in both skills; the article-first content rules live in `.claude/skills/wsj-reading/SKILL.md`. Hard rule: link to WSJ and quote only short phrases — never republish the article text.

## Deploy

GitHub `cosmic-glitch/wsj_club` (public) → Vercel project `wsj_club` (team *Anurag's projects*). **Push to `main` auto-deploys to production** at `wsjclub.vercel.app` — no manual `vercel --prod` needed. `npm run build` validates every content JSON locally.

**Env vars** (for the voice quiz — set in Vercel project settings, and locally in the gitignored `.env.local`): `OPENAI_API_KEY` (required), `AUTH_USERS` (base64 bcrypt logins — see Voice quiz above; no login works without it), `AUTH_SECRET` (a long random string), `ADMIN_USERS` (comma-separated usernames allowed into `/admin`; **set this to your own username** or no one can see the report cards — fail closed), `BLOB_READ_WRITE_TOKEN` (auto-added when a Vercel Blob store is linked; `vercel env pull` to get it locally), and optionally the voice-quiz model knobs `TUTOR_MODEL`, `TTS_MODEL`, `TTS_VOICE`, `STT_MODEL`, `REPORT_MODEL` (see *Models/voice* above). The voice quiz is inert (returns a clean error) until `OPENAI_API_KEY` is set; saving to Blob is best-effort and won't break a session if `BLOB_READ_WRITE_TOKEN` is missing.

**Already provisioned in Vercel** — no need to re-do setup: `OPENAI_API_KEY`, `AUTH_USERS`, and `AUTH_SECRET` are set for **Production + Preview** (marked *sensitive*, so they're intentionally absent from the Development scope and from `vercel env pull`), and a linked Blob store **`wsj-club-quizzes`** supplies `BLOB_READ_WRITE_TOKEN` to all environments. The working copies also live in the local gitignored `.env.local`. `ADMIN_USERS` is **provisioned to `anurag`** (Production + Preview, and in `.env.local`), so `/admin` is unlocked for that teacher login; admin is additive, so `anurag` is also a normal `AUTH_USERS` login who can take the voice quiz. The other logins (`anusha`, `samaira`, `arjun`, `mehar`) are students — voice quiz only. (To change teachers, edit the comma-separated `ADMIN_USERS` in both scopes and `.env.local`, then redeploy.) For a fresh checkout, recreate `.env.local` by hand (the sensitive values aren't pullable) — at minimum `OPENAI_API_KEY`, `AUTH_SECRET`, an `AUTH_USERS` from the hash script, `ADMIN_USERS`, and `BLOB_READ_WRITE_TOKEN` (pullable via `vercel env pull`).
